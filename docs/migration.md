# Перенос данных заказчика: решение и состояние контура

Пункт плана **migrate-run**. Пункт был задуман как перенос старой клиентской
базы и справочников заказчика в рабочий контур с пробным и боевым прогоном
импорта (`docs/import.md`), сверкой контрольных цифр и двухнедельным
параллельным периодом со старым учётом.

## Решение 18.09.2026: переносить нечего

Файлов старого учёта у заказчика нет. Ответ владельца проекта 18.09.2026 на
запрос данных: «данных для переноса нет, все будут наполнять вручную по мере
появления клиентов и заказов». Отсюда:

- **Клиентская база начинается с нуля.** Карточка клиента заводится оператором
  при первом приёме заявки (экран «Приём заявки», проверка дублей по телефону), история
  по телефону накапливается из заявок и актов системы. Таблица `client_history`
  остаётся пустой: строк старого учёта, которые в неё ложатся, не существует.
- **Справочники уже загружены** книгой пункта `req-refs` в день очистки контура
  (`live-ip`): 30 городов, 5 услуг, 6 типов приборов. Цены и ставки руководитель
  правит на экране «Услуги и ставки»; города и типы приборов интерфейсом не
  правятся — при изменениях книгу справочников грузят импортом повторно
  (`npm run import -- refs …`), повторный запуск ничего не задваивает.
  Методика поверки и интервалы для «Аршина» (замечание 4г `docs/uat.md`)
  доезжают тем же путём.
- **Сотрудники** — заводит заказчица на экране «Сотрудники»; в базе две
  учётные записи с логином, `owner` и `berdinskikh`, обе с полным доступом.
- **Параллельный период и акт сверки не нужны:** сверять систему не с чем.
  Переход со старого учёта на систему целиком описан планом запуска
  (`docs/launch.md`): старый файл или журнал с недели 2 пилота переводится в
  режим чтения и отключается письменным решением заказчицы. История по старым
  клиентам, пока она нужна для справок, смотрится там же.

Запрос данных заказчице и форма акта сверки, подготовленные до ответа, из
файлов чатов убраны; собирающий их скрипт остался в песочнице владельца
(`build_migration_docs.js`) на случай, если данные всё-таки появятся.

## Состояние рабочего контура на 18.09.2026

Снято на машине контура (`crm-uchetkin-prod`) запросом к базе `uchetkin`:

| Таблица | Строк | Что это |
| --- | --- | --- |
| `cities` | 30 | города и расписание выездов из книги `req-refs` |
| `services` | 5 | услуги, цены и ставки |
| `device_types` | 6 | типы приборов и межповерочные интервалы |
| `staff` | 2 | обе строки — учётные записи с логином (`owner`, `berdinskikh`) |
| `clients`, `client_history`, `requests`, `routes`, `photos`, `audit_log` | 0 | данных заказчика в системе ещё нет |

Копии базы идут по таймеру `uchetkin-backup` в бакет `uchetkin-dev-ops`
(`pg/daily`), последний запуск 18.09.2026 завершён успешно. Отдельной копии
«перед боевым прогоном» нет — прогона не было.

## Если файлы старого учёта всё же появятся

Порядок остаётся тем, что заложен в `docs/import.md`; персональные данные
клиентов при этом не покидают машину контура:

1. Файлы (книга справочников по шаблону и выгрузка клиентской базы как есть)
   кладутся на машину контура в `/opt/uchetkin/import/`; из файлов чата и с
   машины шлюза копии удаляются.
2. Копия базы: `sudo systemctl start uchetkin-backup`, строка «→ s3://…» из
   `sudo journalctl -u uchetkin-backup -n 3` записывается сюда. Восстановление
   копии проверяется в отдельную базу того же контейнера
   (`createdb uchetkin_restore_check` + `pg_restore`), затем база удаляется.
3. Пробный прогон на машине контейнером `node:22-alpine` с исходниками
   `/opt/uchetkin/src/server` (как `uat-stand.sh`): `npm run import -- refs …
   --dry-run --report …`, затем `clients … --map … --dry-run --report …`.
   Отчёт `.xlsx` — в бакет `uchetkin-dev-ops`, папка `import/`; владельцу —
   только путь. Порог: отвергнутых строк меньше 2 %.
4. Заказчица правит строки по отчёту, прогон повторяется тем же файлом.
5. Боевой прогон без `--dry-run`, контрольные цифры (число клиентов, заявок за
   последний месяц, суммы по прайсу) сверяются с цифрами заказчицы, акт сверки
   подписывается. После прогона `select count(*) from staff where login is not
   null` по-прежнему равен двум: импорт учётных записей не заводит.
6. Две недели старый учёт и система ведутся параллельно с ежедневной утренней
   сверкой заявок за вчера оператором; решение об отключении старого учёта —
   письменное, за заказчицей (форма — в `docs/launch.md`).
