# Эквайринг и фискализация

Пункт плана **int-pay**. Схема выбрана в пункте **req-pay** («Учёткин — эквайринг
и фискализация, решение», 18.09.2026): основной способ — оплата по QR СБП,
резерв — платёжная ссылка, чек — облачная касса с отправкой клиенту, терминалы
не подключаются. Наличные остаются: поверитель берёт их на адресе и держит как
подотчёт, как и раньше (**fe-payment**).

## Кто провайдер

Решение req-pay оставило выбор за ответом УБРиР: даёт ли банк заказчика API для
QR под каждую заявку и присылает ли событие об оплате. На момент этого пункта
ответа нет (опросный лист № 2, вопросы 4–6 раздела «Эквайринг»), поэтому первая
реализация сделана под запасной вариант из того же решения — платёжный сервис, у
которого СБП, ссылка и чеки через партнёрскую кассу лежат в одном договоре:
**ЮKassa** (`server/src/payment/yookassa.ts`). Один договор и один кабинет вместо
трёх, СБП по тарифу Банка России, чеки «от ЮKassa» без своей кассы.

Код от провайдера не зависит: обработчики и экраны знают только интерфейс
`PaymentProvider` (`server/src/payment/provider.ts`) — создать платёж, прочитать,
отменить, вернуть, зарегистрировать чек, подтвердить уведомление. Если УБРиР
ответит «да», банк добавляется своей реализацией интерфейса и переменной
`PAYMENT_PROVIDER`; таблицы, экраны и сверка остаются те же.

## Как это работает

```
акт ──«СБП по QR» / «платёжная ссылка»──▶ POST /api/requests/{id}/online-payment
      ◀── QR (SVG) или ссылка ── провайдер создал платёж на сумму акта
клиент платит в приложении банка ──▶ провайдер ──уведомление──▶ POST /api/webhooks/payment/{секрет}
      ──▶ «оплачен» ──▶ чек в кассе с позициями акта ──▶ чек на почту клиента
      ──▶ номер чека в заявке ──▶ уведомление «чек отправлен» (int-notify)
руководитель ──▶ сверка за день, CSV бухгалтеру, возврат с чеком, отмена
```

1. **Поверитель** в акте выбирает «СБП по QR» или «платёжная ссылка» и жмёт
   «Показать QR» (или «Показать ссылку»). Сумму он не вводит: сервер считает
   цену акта по строкам приборов — со скидкой пенсионеру, за счёт компании, — и
   создаёт платёж ровно на неё. Повторное нажатие отдаёт тот же платёж.
2. **Клиент** сканирует код приложением банка (или открывает ссылку — картой
   или СБП на странице провайдера). Окно на телефоне опрашивает сервер раз в
   четыре секунды; кнопка «Проверить оплату» спрашивает провайдера сразу.
3. **Провайдер** присылает уведомление на приёмник. Приёмник проверяет секрет в
   адресе, адрес отправителя по списку провайдера и **перечитывает платёж из
   API провайдера** — состояние и сумма берутся оттуда, а не из тела
   уведомления. Подписи у уведомлений ЮKassa нет; это её рекомендованный порядок
   подтверждения, и он строже подписи: подделать ответ API нельзя.
4. Платёж становится **«оплачен»**, в заявке появляется отметка `paid_at`,
   сумма — та, что пришла. Сервер регистрирует в кассе **чек** с позициями акта:
   одна строка прибора — одна позиция (услуга · тип прибора · заводской номер),
   цена со скидкой, признак «услуга», способ «полный расчёт», ставка НДС и система
   налогообложения из настроек контура. Касса отправляет чек клиенту на почту
   из заявки (нет почты — по номеру телефона, СМС).
5. **Номер чека** ложится в заявку (`payments.receipt_number`) и в платёж; в очередь
   уведомлений ставится событие **«чек»** — письмо и СМС клиенту с номером чека
   и суммой (с его согласия, как и всё в int-notify).
6. **Закрыть позицию** безналом можно и до оплаты — тогда акт закрыт, а заявка
   «ждёт оплаты» до уведомления. Сумма в отметке — из платежа; отметка
   «оплачено» — только от провайдера, руками её не поставить.

Подотчёт поверителя безнал **не трогает**: деньги ушли на расчётный счёт ИП.
`GET /api/handovers` считает наличные и переводы, как раньше; безнал считается
отдельно — карточкой «Безнал по эквайрингу · сверка за день» на странице
руководителя «Сдельная оплата», с итогами и выгрузкой.

## Правила, которые держит сервер

| Правило | Где |
|---|---|
| Сумма платежа = цена акта на момент создания. Изменился акт — позицию с этим платежом не закрыть и отметку не поставить: «Создайте QR заново — старый отменится» | `openPaymentProblem` в `src/payment/service.ts`, вызывается из `close` и `PUT /payment` |
| Оплата пришла не на ту сумму (или акт правили после оплаты) — платёж помечен `mismatch`, сумма в заявке — фактическая, руководитель видит в сверке | `applyEvent` |
| Уведомление обрабатывается один раз: ключ повтора `payment_events.dedup_key` (провайдер + событие + объект + состояние) и переходы «только вперёд» | `POST /webhooks/payment/:secret`, `applyEvent` |
| Чужой секрет, чужой адрес, платёж, которого у провайдера нет, — 403/400, событие записано с причиной; состояние не меняется | приёмник |
| Возврат и отмена — только руководитель; причина возврата обязательна; действие попадает в журнал (`audit_log`, сущность `online_payments`) | `POST /online-payments/:id/refund`, `/cancel`; `src/api/audit.ts` |
| Оплаченный безнал наличными не перекрыть и «вернуть в работу» не снять — только возврат | `close`, `reopen` |
| Закрытие наличными при ожидающем QR отменяет QR у нас (провайдер свой отменит по сроку) | `close` |
| Без ключей провайдера безналичных способов нет: `payMethods()` их не отдаёт, `POST /online-payment` — 503, `PUT /payment` с таким способом — 422 | `src/payment/config.ts` `canPay` |
| Ожидающий платёж старше `PAYMENT_TTL_MINUTES` (час) отменяется у нас: `npm run payment:expire` | `expireStale` |

Возврат: провайдер возвращает деньги на тот же счёт клиента и пробивает **чек
возврата** (позиции передаются в запросе возврата); заявка становится «не
оплачено» с причиной в примечании — она видна в «выполнено без оплаты», как
любой долг.

## Данные

Миграция `server/migrations/1757981200000_payment.sql`, описание таблиц — в
[`schema.md`](schema.md): `online_payments` (платёж провайдера: вид, сумма-снимок,
состояние, QR или ссылка, позиции чека, чек, возврат), `payment_events`
(уведомления как пришли, включая непринятые), `payments.receipt_number` и два
новых способа в `payments.method`. Событие `чек` — в `notify_templates` и
`notifications`.

## API

| Что | Кому |
|---|---|
| `GET /api/payments/config` — подключён ли эквайринг, какие виды; руководителю ещё адрес приёмника и коды чека | все |
| `POST /api/requests/{id}/online-payment` `{kind: qr\|link}` — платёж на сумму акта | поверитель по своим адресам, остальные |
| `GET /api/requests/{id}/online-payment` — действующий платёж | те же |
| `GET /api/online-payments/{id}` (`?sync=true` — спросить провайдера), `GET …/qr.svg` | те же |
| `GET /api/online-payments?date=…` или `from&to` — сверка: платежи с заявками и итоги | руководитель |
| `GET /api/online-payments/export.csv?date=…` — выгрузка бухгалтеру (Excel, `;`, метка порядка байтов, строка «Итого») | руководитель |
| `POST /api/online-payments/{id}/refund` `{reason}`, `/cancel`, `/receipt` (пробить чек повторно) | руководитель |
| `POST /api/webhooks/payment/{секрет}` — приёмник провайдера | провайдер |

`GET /api/payments/{id}/status` у безнала отдаёт `provider` и состояние платежа
провайдера, у наличных — как раньше. Список заявок с `with=payment` и карточка
заявки отдают ещё `online` — действующий платёж.

## Настройка контура

Переменные — `server/env.example`, раздел «Эквайринг». В облаке ключи приходят
из Lockbox по сервисному аккаунту ВМ: секрет `payment` (он заведён Terraform
пустым, `infra/README.md`), записи **`shop_id`**, **`secret_key`**,
**`webhook_secret`** и необязательная `provider`. Пустой секрет — рабочее
состояние: наличные и перевод работают, безнала в акте нет.

| Переменная | Что |
|---|---|
| `PAYMENT_PROVIDER` | `yookassa`; не задана — ЮKassa, если есть ключи |
| `PAYMENT_SHOP_ID`, `PAYMENT_SECRET_KEY` | из кабинета провайдера (тестовый магазин — тестовые, боевой — боевые) |
| `PAYMENT_WEBHOOK_SECRET` | секрет в адресе приёмника; адрес для кабинета — `GET /api/payments/config` (руководитель) |
| `PAYMENT_ALLOWED_IPS` | адреса провайдера через запятую; не задана — список ЮKassa из документации |
| `PAYMENT_TAX_SYSTEM` | система налогообложения в чеке: `2` — УСН доходы (по умолчанию), `3` — УСН доходы минус расходы. Объект налогообложения заказчика — вопрос 1 опросного листа № 2 |
| `PAYMENT_VAT_CODE` | ставка НДС по позициям: `1` — без НДС (по умолчанию) |
| `PAYMENT_TTL_MINUTES` | сколько живёт неоплаченный QR или ссылка у нас (60) |
| `PAYMENT_API_URL` | адрес API; меняется только на эмулятор |
| `PUBLIC_BASE_URL` | от него считается адрес приёмника и страница возврата после оплаты по ссылке |

### Подключение у заказчика

1. Договор с провайдером на ИП, в кабинете — тестовый магазин. Тестовые
   `shopId` и секретный ключ — в Lockbox `uchetkin-dev-payment` (dev),
   `webhook_secret` — любая длинная случайная строка.
2. В кабинете провайдера: адрес уведомлений — `GET /api/payments/config` от имени
   руководителя показывает `webhook_url`; включить события `payment.succeeded`,
   `payment.canceled`, `refund.succeeded`. Уведомления приходят только на HTTPS с
   именем — контур уже на `https://uchetkin.ru` (**cloud-domain**).
3. «Чеки от ЮKassa» в кабинете: система налогообложения заказчика, место расчёта
   (адрес при выезде — вопрос 2 раздела «Реквизиты» опросного листа), почта и
   телефон покупателя приходят из заявки.
4. Полный круг в тестовом контуре: QR в акте → тестовая оплата в песочнице
   провайдера → чек в тестовой кассе и на тестовую почту → номер в заявке →
   возврат. То же, что делает `check:payment` на эмуляторе, но с настоящими
   ключами; результат записать в этот документ.
5. Боевые ключи — новой версией того же секрета; `PAYMENT_TAX_SYSTEM` — по
   ответу заказчика. Переход бригад — с первого числа месяца, как в решении
   req-pay.

## Машина разработчика и проверки

Без ключей провайдера: эмулятор HTTP-интерфейса ЮKassa
(`server/src/payment/emulator.ts`) — те же адреса, поля и ошибки, платежи,
возвраты, чеки с «отправкой» на почту, уведомления на приёмник.

```bash
cd server
npm run payment:emulator          # печатает переменные для .env; оплата — кнопкой на /pay/<id>
npm run check:payment             # сквозная проверка по сети: QR → оплата → чек → уведомление → сверка → возврат
npx tsx --test test/payment.test.ts   # правила: позиции чека, сумма = акт, повторы, права, приёмник
cd ../web && npm run build && npm run check:payment-ui   # экраны против настоящего API и эмулятора
```

`check:payment` стоит в цепочке `npm run check` (CI). Чего проверки не проверяют
и проверить не могут: примет ли настоящий провайдер ключи заказчика и
зарегистрирована ли касса на выездные услуги — это шаг 4 подключения.

## Что этот пункт не закрывает

- **Чек на наличные.** Решение req-pay предполагает пробивать через ту же кассу
  и наличные, принятые на адресе. Для этого касса должна быть зарегистрирована
  на выездную торговлю (вопросы 1–3 раздела «Касса» опросного листа). Механика
  готова (`registerReceipt` с `settlement: 'cash'`), включается отдельным
  пунктом после ответа заказчика — иначе система будет требовать чек там, где
  заказчик пока пробивает его иначе.
- **Отправка ссылки СМС из системы.** Ссылку поверитель показывает или копирует
  в мессенджер; своё СМС-событие «ссылка на оплату» добавляется в int-notify по
  запросу заказчика.
- **Банк заказчика вместо сервиса** — по ответу УБРиР, своей реализацией
  `PaymentProvider`.
