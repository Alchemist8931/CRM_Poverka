# Уведомления клиентам: почта и СМС

Пункт плана **int-notify**. Документ отвечает на три вопроса: с какого адреса
уходят письма и почему именно с него, какой СМС-шлюз выбран из трёх и почему,
и как всё это устроено внутри.

Исходники: `server/src/notify/`, маршруты `server/src/api/routes/notify.ts`,
экран руководителя — блок «Шаблоны уведомлений» на странице «Услуги и ставки».

## Главное правило

**Уведомления никого не заменяют.** Дату выезда по-прежнему подтверждает
оператор голосом при обзвоне накануне — так работает контора сегодня, и так она
работает после этого пункта. Письмо и СМС — второй канал к тому же разговору.
Из этого следует всё остальное устройство: упавшая почта не имеет права уронить
приём заявки, ненастроенный шлюз не имеет права потерять сообщение, а сообщение
без согласия клиента не уходит вовсе.

## Отправитель: рабочий ящик конторы, а не технический домен

До пункта **cloud-domain** своего домена у системы нет: она живёт на временном
имени Яндекс Облака. Письмо, отправленное с технического имени вроде
`noreply@xn--...yandexcloud.net`, у которого на домене отправителя нет ни SPF, ни
DKIM, уходит в спам — и настроить это с нашей стороны нельзя никак.

Поэтому отправитель — обычный рабочий ящик конторы в Яндекс 360. Его домен уже
подписан, и для принимающей почты письмо от него ничем не отличается от письма,
написанного руками. Клиент, к тому же, видит знакомый адрес, а не машинный.

Адрес, имя отправителя, подпись и телефон конторы лежат в настройках
(`server/src/notify/config.ts`, переменные `NOTIFY_*`). В день переезда на свой
домен меняется одна строка — `NOTIFY_FROM` — и пароль ящика в Lockbox:

```bash
grep -rn "NOTIFY_FROM" server/src server/scripts   # где адрес вообще берётся
```

Ни в шаблонах, ни в коде, ни в базе адреса отправителя нет.

### Свой почтовый домен (пункт cloud-domain)

Боевой домен системы — `uchetkin.ru` (куплен 20.09.2026). Ящик отправителя
переезжает на него: `uvedomleniya@uchetkin.ru` (или как назовёт заказчица) в
Яндекс 360 для бизнеса на том же домене. Порядок и проверки — `docs/ops.md`,
«Переезд на боевой домен», шаг В. Записи зоны ведёт Terraform (`infra/dns.tf`,
`mail_records_enabled`), сама зона заведена 20.09.2026:

| Запись | Значение | Зачем |
| --- | --- | --- |
| MX `@` | `10 mx.yandex.net.` | входящая почта домена — в Яндекс 360 |
| TXT `@` | `v=spf1 redirect=_spf.yandex.net` | SPF: слать от имени домена можно только серверам Яндекса |
| TXT `@` | `yandex-verification: …` | подтверждение владения доменом для Яндекс 360 (`mail_verification_txt`) |
| TXT `mail._domainkey` | `v=DKIM1; k=rsa; t=s; p=…` | DKIM: подпись письма ключом домена, значение из админки 360 (`mail_dkim_public_key`) |
| TXT `_dmarc` | `v=DMARC1; p=quarantine; rua=mailto:postmaster@uchetkin.ru; adkim=s; aspf=s` | DMARC: неподписанное письмо «от нас» — в спам, отчёты на postmaster |

Что меняется в системе: `NOTIFY_FROM` и `SMTP_USER` в `app.env` на новый ящик,
`smtp_password` в Lockbox `smtp` — пароль приложения нового ящика
(в Яндекс 360 — «Пароли приложений», обычный пароль SMTP не примет). Хост и порт
те же: `smtp.yandex.ru:465`.

Как убедиться, что письма не идут в спам, — три ящика и заголовки:

1. Отправить тестовое письмо через систему на ящики Яндекса, Mail.ru и Gmail:
   три заявки на тестового клиента с этими адресами и согласием на уведомления,
   затем `npm run notify:tick` на машине — письмо «заявка принята» уйдёт на
   каждый; доставка видна в `GET /api/notify/queue`.
2. В каждом ящике письмо должно лежать во «Входящих», не в «Спаме».
3. Открыть «исходное письмо» (Gmail — «Показать оригинал», Яндекс — «Свойства
   письма», Mail.ru — «Заголовки») и найти строку `Authentication-Results`:
   должно быть `spf=pass`, `dkim=pass`, `dmarc=pass`. Один `fail` — искать в
   записях зоны: `dig +short TXT uchetkin.ru`,
   `dig +short TXT mail._domainkey.uchetkin.ru`, `dig +short TXT _dmarc.uchetkin.ru`
   (из песочницы порт 53 наружу закрыт — запросы с узла «Alchemist LAB»).
4. Сохранить результат (три заголовка) в `docs/uat.md`, журнал прогонов, — это
   и есть приложение к сверке пункта `cloud-domain`.

Репутации у нового домена нет, поэтому первые дни объём не наращивать резко:
десятки писем в день, как на пилоте, — норма; тысячи в первую неделю — путь в спам
даже с правильными записями.

### Почему SMTP, а не Yandex Cloud Postbox

Postbox — правильная служба для рассылок с собственного домена: очередь,
подписи, отчёты о доставке. Но он требует того самого домена, которого до
запуска нет, и подтверждения владения им. Пока писем десятки в день и уходят
они с рабочего ящика, простого SMTP достаточно, а переход на Postbox — это
смена трёх переменных `SMTP_*`: интерфейс у него тот же самый.

## СМС-шлюз: сравнение трёх и выбор

Сравнение на 17.09.2026. Цены у операторов меняются, и перед подписанием
договора их надо перепроверить — здесь они для порядка величин и для сравнения
между собой, а не как оферта.

| | [SMSC.ru](https://smsc.ru/api/) | [SMS.RU](https://sms.ru/api) | [МТС Exolve](https://docs.exolve.ru/docs/ru/api-reference/sms-api/) |
|---|---|---|---|
| Интерфейс | HTTP GET/POST, а также SMTP и SMPP | HTTP GET/POST | HTTP + JSON, ключ в заголовке |
| Формат ответа | JSON при `fmt=3` | JSON при `json=1` | JSON |
| Тестовый контур | **виртуальная отправка `virtsms=1`**: шлюз отвечает как при настоящей, абоненту ничего не уходит, деньги не списываются | стартовый баланс и отправка на свой подтверждённый номер | в тестовый период отправка только на свой подтверждённый номер |
| Цена за СМС | от 3,49 ₽ (уведомления дешевле рекламы), триггерные — от 1,49 ₽ | от ~8,4 ₽ по прайсу операторов, тип сообщения меняет цену | по договору, публичного прайса за сообщение нет |
| Имя отправителя | регистрируется у операторов, помесячная плата | 2 080–3 000 ₽/мес за оператора | по договору |
| Что ещё | статусы доставки, баланс, HLR | статусы доставки | голос, мессенджеры, номера — одной платформой |

**Выбран SMSC.ru.** Три причины, в порядке важности:

1. **Тестовый контур без денег и без договора.** `virtsms=1` — это полный путь
   запроса до шлюза с настоящим ответом, но без доставки и без списания. Ровно
   то, что нужно на приёмочных испытаниях (**test-uat**), где операторы будут
   гонять десятки пробных заявок: у двух других тестовая отправка возможна
   только на свой же подтверждённый номер, и проверить рассылку по списку
   нельзя.
2. **Цена видна до договора и считается на калькуляторе.** У Exolve цена за
   сообщение обсуждается, и сравнить её заранее не с чем.
3. **Простой интерфейс.** Логин, пароль, номер, текст — форма и JSON в ответ.
   Клиент целиком (`server/src/notify/sms.ts`) — шестьдесят строк, и в нём
   видно всё, что уходит наружу.

Против SMSC — цена: не самый дешёвый на объёме. Но объём здесь маленький: одна
бригада, десятки выездов в день, четыре события на заявку. При 40 заявках в
день и двух СМС на заявку это около 250 ₽ в день — и в эту сумму заложена
возможность отключить СМС-канал целиком одной галочкой в шаблонах, оставив
почту, если заказчик решит, что дорого.

**Про Yandex Cloud Notification Service.** Он в той же консоли, что и вся
инфраструктура, и платился бы с того же аккаунта — это было бы удобно. Но
отправка СМС там на стадии Preview, а интерфейс совместим с Amazon SNS, то есть
на договор с оператором всё равно выходить отдельно. Возвращаться к нему стоит
после запуска, когда станет понятен настоящий объём.

### Имя отправителя

Пока имя не зарегистрировано, СМС приходят с номера, а не с имени конторы, и
это нормально для пробных отправок. Регистрация имени — платная и помесячная,
поэтому решение о ней принимает заказчик перед пилотом (`SMS_SENDER` в
настройках). Отдельного кода это не требует.

## MAX — точка расширения

Заказчик на вопрос о канале рассылки ответил «МАКС??» — то есть выбор не сделан.
Пока ответа нет, мессенджера в системе нет: канал, которого никто не выбрал,
это не функция, а неподдерживаемый код.

Место под него готово, и добавление — это четыре правки, не считая самого
клиента:

1. `server/src/notify/max.ts` — объект с полем `channel` и методом `send`
   (интерфейс `Notifier`, `server/src/notify/notifier.ts`);
2. `'max'` в тип `Channel` (`server/src/notify/templates.ts`);
3. `'max'` в CHECK у `notify_templates.channel` и `notifications.channel`
   (новой миграцией) плюс восемь строк шаблонов;
4. `max` в перечень отправителей в `notifiers()`.

Ни очередь, ни шаблоны, ни экран руководителя при этом не меняются: они
работают с каналом вообще, а не с почтой и СМС по отдельности.

## События

Четыре события, все — про одну заявку.

| Событие | Когда | Что в сообщении |
|---|---|---|
| `заявка` | сразу после приёма | дата, окно прибытия, адрес, услуги, предварительная сумма по прайсу, способы оплаты на месте |
| `напоминание` | накануне выезда в 18:00 | завтрашняя дата, окно, адрес, телефон для переноса |
| `выезд` | утром в день выезда, в 8:00 | имя поверителя и окно прибытия |
| `перенос` | когда оператор переставил заявку | прежняя и новая дата, окно |

Время — по часовому поясу конторы (`NOTIFY_TZ`, по умолчанию
`Asia/Yekaterinburg`): ВМ стоит в UTC, и в её полночь у клиента ещё вчерашний
вечер.

**Суммы.** В сообщении о заявке стоит *предварительная* стоимость: сумма по
прайсу за услуги, которые клиент назвал при приёме, по цене его типа (физлицо
или юрлицо). Точная сумма появляется в акте — там считают приборы, а пенсионную
скидку ставит поверитель на месте. Способы оплаты — наличные или перевод на
карту: эквайринга нет и до пункта **int-pay** не будет, поэтому ссылку на
оплату обещать нельзя. Событие «чек отправлен» появится там же.

## Согласие клиента

Галочка «Уведомления» в форме приёма (`requests.notify_consent`). Ставит её
оператор со слов клиента. Без неё не уходит ничего — проверка одна и стоит в
одном месте, в `enqueue()` (`server/src/notify/events.ts`), поэтому обойти её
новым событием физически негде.

Согласие запоминается и в карточке клиента: при следующем звонке оператор видит
его в подстановке адреса и не спрашивает второй раз. Отозванное согласие снимает
с очереди всё, что ещё не ушло (`cancelStale`), — с пометкой причины, а не
удалением.

## Очередь, повторы и журнал доставки

Обработчик запроса ничего не отправляет. Он кладёт готовое сообщение в таблицу
`notifications`, а отправкой занимается проход очереди:

```bash
cd server
npm run notify:tick           # снять отменённое, поставить срочное, отправить готовое
npm run notify:tick -- --plan # только поставить в очередь
```

На машине приложения это таймер раз в четверть часа (рядом с `audit:prune`,
пункт **cloud-ops**). Чаще незачем: напоминание и утреннее сообщение ставятся в
очередь заранее, со своим сроком отправки, и проход только забирает то, чему
срок подошёл.

- **Текст складывается в строку в момент события**, а не при отправке: шаблон
  руководитель может поправить в любую минуту, а клиент должен получить то, что
  ему обещали. По той же причине в строке лежит и адрес.
- **Повтор ждёт дольше с каждым разом**: 10, 20, 40, 80 минут
  (`NOTIFY_RETRY_MINUTES`). После пяти попыток (`NOTIFY_MAX_ATTEMPTS`)
  сообщение останавливается в состоянии «ошибка» с причиной от шлюза — и
  остаётся видно руководителю, а не исчезает.
- **Канал без ключей молчит, но очередь не теряет.** Нет пароля ящика —
  письма ждут его, не тратя попыток.
- **Каждая попытка пишется строкой** в `notification_attempts`: очередь
  отвечает на вопрос «дошло ли», журнал — «что было по дороге».

Смотрит руководитель: `GET /api/notify/queue` с отбором по состоянию, событию,
каналу и заявке; `GET /api/notify/queue/:id/attempts` — попытки одного
сообщения. Оператору журнал доставки не отдаётся: в нём телефоны и адреса
клиентов.

## Шаблоны

Тексты правит руководитель на странице «Услуги и ставки», блок «Шаблоны
уведомлений»: восемь штук — четыре события на два канала. У письма правится
тема и текст, у СМС — только текст. Галочка «Отправляем» выключает канал по
событию, не трогая остальные.

Подстановки пишутся в фигурных скобках и перечислены прямо над полями:
`{имя}`, `{дата}`, `{окно_с}`, `{окно_до}`, `{адрес}`, `{услуги}`, `{сумма}`,
`{оплата}`, `{поверитель}`, `{прежняя_дата}`, `{контора}`, `{телефон_конторы}`,
`{подпись}`. Часть из них у события отсутствует по смыслу — имени поверителя в
момент приёма заявки ещё нет, маршрут собирается позже, — и сервер такой шаблон
не примет, назвав причину. Опечатка ловится там же: «Неизвестная подстановка
{мастера}». Это нарочно: непойманная опечатка уезжает клиенту в виде
`{мастера}` посреди письма, и узнаём мы об этом от него.

## Настройка контура

Переменные и что они значат — `server/env.example`, раздел «Уведомления
клиентам». В облаке пароль ящика и ключи шлюза приходят из Lockbox по
сервисному аккаунту ВМ (`LOCKBOX_NOTIFY_SECRET_ID`, записи `smtp_password`,
`sms_login`, `sms_password`); в репозитории, в образе и в переменных выкладки их
нет — правило то же, что у остальных секретов (`server/src/secrets.ts`).

Что нужно от заказчика, чтобы канал ожил:

1. адрес рабочего ящика и **пароль приложения** к нему (не пароль входа —
   отдельный, из настроек Яндекс 360);
2. учётная запись на SMSC.ru: логин, пароль, при желании — имя отправителя;
3. телефон конторы для подписи в сообщениях.

До этого система работает целиком: сообщения ставятся в очередь и ждут.

## Проверки

```bash
cd server
npm test -- test/notify.test.ts   # правила: согласие, шаблоны, очередь, повторы, роли
npm run check:notify              # сквозная: письмо и СМС уходят по протоколу
cd ../web
npm run build && npm run check:notify-ui   # экраны: галочка, очередь, блок шаблонов
```

`check:notify` поднимает на свободных портах настоящий SMTP-приёмник и эмулятор
HTTP-интерфейса SMSC, прогоняет все четыре события и читает то, что улетело:
адрес отправителя, заголовки письма, кодировку темы, заполненность подстановок,
`virtsms=1` у СМС, журнал попыток и отложенный повтор при недоступном сервере.
Чужих служб и чужих счетов она не трогает.

**Чего ни одна проверка не проверяет:** попадёт ли письмо во «Входящие» или в
«Спам» у настоящего получателя. Это решает принимающая почта по подписи домена
отправителя, и увидеть это можно только глазами в ящике:

```bash
cd server
npm run notify:probe -- --to проверка@пример.рф   # письмо с боевого ящика
npm run notify:probe -- --sms +79001234567        # СМС через шлюз
```

Эту команду прогоняют дважды: когда заказчик даст доступ к ящику, и ещё раз в
день переезда на свой домен (**cloud-domain**).
