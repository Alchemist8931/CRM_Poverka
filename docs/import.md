# Импорт данных заказчика

Пункт плана **be-import**. Как перенести в «Учёткин» то, что у заказчика уже есть:
книгу справочников, заполненную по нашему шаблону, и клиентскую базу из старого
учёта. Код — `server/scripts/import/`, запуск — `npm run import` в каталоге `server`.

## Коротко

```bash
cd server
npm run import -- refs «Учёткин — справочники.xlsx» --dry-run --report отчёт.xlsx
npm run import -- refs «Учёткин — справочники.xlsx»
npm run import -- clients «база.xlsx» --map import-map.json --dry-run --report отчёт.xlsx
npm run import -- clients «база.xlsx» --map import-map.json
```

Порядок обязателен: сначала справочники, потом клиенты. Город клиента — ссылка на
справочник городов, а срок следующей поверки считается по межповерочному интервалу
из справочника приборов; без справочников то и другое останется пустым.

| Ключ | Что делает |
|---|---|
| `--dry-run` | ничего не пишет: показывает, что будет создано, обновлено и отвергнуто |
| `--report <файл.xlsx>` | отчёт об отвергнутых строках и замечаниях — его отдают заказчику |
| `--map <файл.json>` | карта столбцов клиентской базы, см. `server/scripts/import-map.example.json` |
| `--sheet <название>` | лист книги, если он не первый |
| `--city <город>` | город для строк, где город не указан |

Код возврата: `0` — прогон состоялся (даже если часть строк отвергнута), `1` — не
состоялся вовсе: нет файла, не та команда, не нашёлся столбец с телефоном.

## Два свойства, на которых всё держится

**Пробный прогон показывает правду.** `--dry-run` — не отдельный код «как будто»:
работает тот же загрузчик, в той же транзакции, и в конце она откатывается.
Поэтому цифры пробного прогона и есть цифры боевого.

**Повторный запуск ничего не меняет.** Каждая строка кладётся через
`INSERT ... ON CONFLICT DO UPDATE ... WHERE строка и правда изменилась`. Во второй
раз всё уходит в столбец «без изменений», и `updated_at` не шевелится. Отсюда и
рабочий порядок с заказчиком: он присылает файл — мы грузим — он находит в отчёте
свои же ошибки, правит их и присылает снова, а мы грузим тот же файл ещё раз.
Задвоения не будет, поправленное подхватится.

## Справочники: `refs`

Книга — та, что ушла заказчику в пункте **req-refs** (копия лежит в
`server/test/fixtures/refs-template.xlsx`).

| Лист книги | Куда ложится |
|---|---|
| «Города» | `cities`: название, крупный или малый, дни недели выезда, норматив адресов |
| «Услуги и прайс» | `services`: группа, название, три цены, две сдельные ставки |
| «Приборы» | `device_types`: название, номер в ГРСИ, межповерочный интервал |
| «Сотрудники» (необязательный) | `staff`: ФИО, роль, телефон, внутренний номер, график |
| «Компетенции» (необязательный) | `staff_skills`: допуск «да» заводит, «нет» снимает |
| «Формы» | никуда: бланки и их нумерация — печатные формы, пункт **fe-forms** |

Столбцы ищутся по названию, а не по месту: заказчик может переставить их местами.
Строки-примеры из шаблона грузятся как обычные — они и есть данные прототипа.

Чего в книге нет и что импорт придумывает сам, **один раз**:

- `cities.short` — сокращение для плиток: «Нижний Тагил» → «НТ», «Асбест» → «АСБ».
  У города, который уже заведён, сокращение не меняется: руководитель мог поправить.
- `services.id` — обозначение услуги. Услуги прототипа узнаются по названию и
  получают свои же обозначения (`wv`, `wr`, `hv`, `hm`, `hd`) — на них ссылаются
  правила и строки актов; новым услугам обозначение собирается из названия.
- `device_types.carrier_kind` — вода или тепло, видно по названию прибора;
  когда не видно, тип грузится как «Вода» и строка попадает в замечания.
- `services.replacement_service` — чем меняют непригодный прибор. Проставляется
  только для пар прототипа (поверка воды → замена воды, поверка тепла → монтаж).

### Учётные записи импорт не заводит

Ни одной. Лист «Сотрудники» — это справочник людей: ФИО, роль, телефон, график.
`login`, `password_hash`, `otp_hash` и `mfa_secret` остаются пустыми. Так решил
владелец: учётки заранее не заводятся, руководитель создаёт сотрудника в интерфейсе
по мере найма (пункт **be-users**). Проверяется тестом и сквозной проверкой
`npm run check:import` — счёт строк `staff` с логином или паролем после импорта
обязан быть нулём.

## Клиентская база: `clients`

Приходит как есть: выгрузка из 1С, таблица менеджера, экспорт из старой программы.
Поэтому соответствие «поле системы → столбец заказчика» вынесено в конфиг
(`--map`), а обычные названия («Телефон», «Адрес», «ФИО», «Дата последней поверки»
и прочие) известны импорту и без него. Заготовка — `server/scripts/import-map.example.json`.

Что происходит со строкой:

1. **Телефон** приводится к десяти цифрам: восьмёрка, `+7`, скобки, дефисы и
   добавочный отбрасываются. Строка без разборного телефона отвергается — привязать
   её не к чему.
2. **Дубли склеиваются по телефону**: один и тот же человек, записанный трижды,
   становится одним клиентом. Если ФИО в этих строках разные, берётся первое,
   а расхождение уходит в замечания.
3. **Адрес разбирается по мере возможности** на город, улицу, дом и квартиру.
   Понимаются «г. Асбест, ул. Ленина, д. 12, кв. 5», «Асбест, Ленина 12-5»,
   «ул. 8 Марта, 12а кв 77»; подъезд и этаж отрезаются в примечание. Исходная
   строка сохраняется рядом целиком: разбор угадывает, исходник — нет.
4. **Приборы** разбираются из ячейки: «Бетар СХВ-15 №12345678; Бетар СГВ-15 №…» —
   это две записи с заводскими номерами.
5. **Срок следующей поверки** считается как дата последней плюс межповерочный
   интервал типа прибора. Тип не из справочника — срок остаётся пустым, и строка
   уходит в замечания: выдумывать сроки поверки нельзя.

Карточку клиента, которая уже есть в системе, импорт **не перезаписывает**:
заполняются только пустые поля. Оператор, поправивший ФИО руками, важнее выгрузки
десятилетней давности.

### Куда ложится клиентская база

`clients` — карточка (телефон, ФИО, тип, город), `client_history` — то, что было
в старом учёте: адрес, прибор, дата прошлой поверки и `due_on` — когда клиенту
пора звонить. Почему отдельная таблица, а не «выполненные заявки»: у строки из
старой таблицы нет ни дня выезда, ни маршрута, ни поверителя, ни акта, ни денег.
Записать её заявкой значило бы сочинить выезд, которого не было, и испортить любой
отчёт по датам и сдельной оплате. Подробнее — в [`schema.md`](schema.md).

## Отчёт заказчику

`--report отчёт.xlsx` кладёт рядом файл с тремя листами:

- **Отвергнутые строки** — лист, номер строки, причина словами и сама строка целиком;
- **Замечания** — строки, которые загружены, но что-то в них пришлось угадать;
- **Сводка** — что и сколько создано, обновлено, оставлено без изменений.

Отчёт пишется и в пробном прогоне: он про строки файла, а не про содержимое базы.

## Проверка

```bash
cd server
npm test                  # разбор телефонов и адресов, склейка дублей, идемпотентность
npm run check:import      # тот же импорт через командную строку, на временной базе
```

`check:import` — сквозная: поднимает временную базу, гоняет `npm run import`
пробным и боевым прогоном, повторяет боевой и сверяет, что в базе ничего не
изменилось, проверяет коды возврата на несуществующем файле и неизвестной команде
и считает учётные записи, созданные импортом (должно быть ноль).

## Что дальше

Перенос настоящих данных в prod, сверка с заказчиком и параллельный период со
старым учётом — пункт **migrate-run**. Показ перенесённой истории в карточке
клиента и обзвон «кому пора поверяться» по `client_history.due_on` в объём этого
пункта не входят: таблица заполнена, экраны — отдельная работа.
