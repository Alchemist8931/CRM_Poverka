# Релиз и откат

Пункт плана `cloud-cicd`. Одна страница на два вопроса: как выложить и как
вернуть обратно, если выложенное не работает.

## Как устроено

| Что | Где описано | Когда срабатывает |
| --- | --- | --- |
| Проверки | `.github/workflows/ci.yml` | каждый push и pull request: типы, `npm run check`, тесты сервера, сборка фронта, actionlint |
| Выкладка в dev | `.github/workflows/deploy-dev.yml` | push в `main` — сама, без кнопки |
| Выкладка в prod | `.github/workflows/deploy-prod.yml` | только руками, с выбором тега и подтверждением |
| Сами шаги выкладки | `.github/workflows/deploy.yml`, `deploy/deploy.sh` | вызываются обоими контурами — шаги у dev и prod одни и те же |
| Что запускается на машине | `deploy/compose.yml`, `deploy/Caddyfile` | едут на ВМ на каждой выкладке |

**Тег релиза — короткий SHA коммита** (12 знаков). Плавающих тегов вроде
`latest` нет: по ним не сделать ни откат, ни разбор «когда это сломалось».

**Секретов выкладка не носит.** У GitHub есть ровно два: ключ сервисного
аккаунта для публикации образов и ключ SSH до машины. Пароль к базе, ключ
подписи сессий и ключи внешних служб приложение читает само при старте из
Lockbox по сервисному аккаунту ВМ (`server/src/secrets.ts`).

## Порядок релиза

1. Правка уезжает в `main`. Проверки идут на каждый push, но выкладку не
   держат: в `main` попадает уже проверенное.
2. **Сборка.** `deploy-dev.yml` собирает два образа — `uchetkin-api` из
   `server/` и `uchetkin-web` из `web/` — и кладёт их в Container Registry
   контура с тегом по SHA.
3. **Выкладка в dev.** По SSH на ВМ запускается `deploy/deploy.sh`:
   - копия конфигурации из `/etc/uchetkin/app.env` (её пишет cloud-init);
   - вход в реестр по сервисному аккаунту машины, `docker compose pull`;
   - **миграции отдельным шагом**: `docker compose run --rm api npm run migrate:cloud`
     — до перезапуска, на ещё работающем старом коде;
   - `docker compose up -d`;
   - проба живости: `/health` должен ответить 200 за две минуты, иначе шаг
     падает и в журнал прогона выводятся `docker compose ps` и последние сто
     строк журнала API.
4. **Проверка в dev руками.** Всё, что выложено в prod, до этого работало в dev.
5. **Выкладка в prod.** Actions → «Выкладка в prod» → Run workflow → тег из
   шага 2. Прогон останавливается и ждёт подтверждения (окружение `prod`,
   Required reviewers). После «Approve» идут те же шаги, что и в dev.

Порядок «сначала миграции, потом перезапуск» обязателен: новый код на старой
схеме падает сразу. Обратное — старый код на новой схеме — переживается, если
миграция не удаляет и не переименовывает то, чем пользуется прежняя версия.
**Поэтому миграции пишутся совместимыми с предыдущим релизом**: удаление
столбца — отдельным релизом после того, как его перестали читать. Это не
пожелание, а условие, при котором работает откат.

## Откат

Откат — это тот же «Выкладка в prod», запущенный с тегом предыдущего релиза.
Ничего не пересобирается: образ с этим тегом лежит в реестре.

1. Взять тег предыдущего релиза: журнал прогонов Actions или файл
   `/opt/uchetkin/releases.log` на машине — в нём строки «когда, какой тег,
   какой был до него».
2. Actions → «Выкладка в prod» → Run workflow → этот тег → подтвердить.
3. Убедиться, что `/health` отвечает 200 (это проверяет сам скрипт) и что
   система работает.

**Схему базы откат не трогает.** `migrate:cloud` применяет только недостающие
миграции, вниз не ходит. Если сломала именно миграция, откат кода не поможет:
нужно решение человека — либо правка вперёд новым релизом (обычный случай),
либо `npm run migrate:down` на машине руками с осознанной потерей данных, либо
восстановление базы из резервной копии (пункт `cloud-ops`). Автоматического
отката схемы нет намеренно: молча удалять данные хуже, чем остановиться.

## Что должно быть настроено

Один раз на репозиторий — **переменные** (Settings → Secrets and variables →
Actions → Variables) и **секреты**; в prod они задаются на уровне окружения.

| Имя | Тип | Значение |
| --- | --- | --- |
| `YC_REGISTRY_ID` | переменная | вывод Terraform `registry_id` (`crp...`) |
| `DEPLOY_HOST` | переменная | адрес ВМ контура (`app_external_ip`) |
| `DEPLOY_USER` | переменная | пользователь ВМ (`vm_user`, по умолчанию совпадает с `infra/variables.tf`) |
| `DEPLOY_KNOWN_HOSTS` | переменная | вывод `ssh-keyscan <адрес>`. Не задана — ключ хоста принимается без проверки, и прогон об этом предупреждает |
| `APP_URL` | переменная | адрес системы, показывается ссылкой у прогона |
| `YC_SA_KEY` | секрет | `yc iam key create --service-account-name uchetkin-<контур>-deployer --output key.json`, содержимое файла целиком |
| `DEPLOY_SSH_KEY` | секрет | закрытый ключ SSH выкладки; открытая половина — в `ssh_public_keys` контура |

Окружения (Settings → Environments):

- `dev` — без ограничений, выкладывается само;
- `prod` — **Required reviewers** (заказчик или ответственный за релиз) и
  ограничение веток (`main`). Без этого «по кнопке» превращается в «кто угодно
  и когда угодно».

## Чего ещё нет

- **Доступ по SSH с runner'ов GitHub.** В `infra/dev.tfvars` список
  `ssh_allowed_cidrs` пуст — порт 22 не открыт вовсе. Пока адреса не открыты,
  выкладка дойдёт до шага SSH и остановится по таймауту. Варианты: внести в
  `ssh_allowed_cidrs` диапазоны Actions (`https://api.github.com/meta`, раздел
  `actions`) — их много и они меняются; либо поднять свой runner в том же
  каталоге облака и ходить на машину по внутреннему адресу — так правильнее и
  дешевле по правам. Решается вместе с пунктом `cloud-apply`.
- **Проверка собранных образов.** `docker build` обоих образов и запуск
  `docker compose up` проверяются на машине разработчика и на runner'е при
  сборке; отдельного прогона e2e против свежевыложенного dev в workflow нет —
  это пункт `test-uat`.
- **Наполнение базы демо-данными в dev.** Выкладка его не делает: `npm run seed`
  запускается руками, когда контур нужно набить (`server/README.md`).
