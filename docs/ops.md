# Эксплуатация: оповещения, журналы, резервные копии, восстановление

Пункт плана `cloud-ops`. Страница для того, кто получил оповещение и должен
понять, что случилось и что делать, — без администратора под рукой. Как это
описано кодом — `infra/README.md`, раздел «Эксплуатация».

## Что и где смотреть

| Что | Где | Зачем |
| --- | --- | --- |
| Оповещения | Telegram-бот и почта (см. «Как включить каналы») | узнать о проблеме, не заглядывая никуда |
| Дашборды | консоль облака → Monitoring → Дашборды → `uchetkin-<контур>-vm`, `-http`, `-postgres` (prod) | посмотреть, что происходило с машиной, запросами и базой |
| Журналы приложения | консоль облака → Cloud Logging → группа `uchetkin-<контур>-app` | найти ошибку по времени или по номеру заявки; хранятся 30 дней |
| Журнал сторожа | та же группа, ресурс `serverless.function` | каждая проверка (раз в минуту) и каждое отправленное оповещение с полным текстом |
| Резервные копии базы | консоль → Object Storage → бакет `uchetkin-<контур>-ops`, папки `pg/daily` (14 дней) и `pg/weekly` (год) | восстановить базу |
| Автоматические копии Managed PostgreSQL (prod) | консоль → Managed Service for PostgreSQL → кластер → Резервные копии | восстановить кластер целиком на момент времени, 14 дней |
| Снимки диска ВМ (prod) | консоль → Compute Cloud → Снимки | вернуть машину, если сломалась она сама |

Сторож проверяет систему **снаружи** облака раз в минуту: открывает `/health`,
читает служебные метрики машины и счётчики Caddy, при включённом TLS проверяет
сертификат. Об одной проблеме он пишет один раз, потом напоминает каждые
6 часов, пока она не пройдёт, и пишет «прошло», когда всё вернулось.

## Оповещения: что значит и что делать

Все команды ниже выполняются на машине контура (`crm-uchetkin-prod` в dev):
консоль облака → Compute Cloud → машина → «Серийная консоль», либо SSH, если
он открыт. Команды начинаются с `sudo`.

| Оповещение | Что значит | Что делать по порядку |
| --- | --- | --- |
| 🔴 **Система недоступна** | `/health` не отвечает две минуты подряд. Либо остановилось приложение, либо машина, либо сеть до неё | 1. Открыть систему в браузере: если открывается — ложная тревога сети, подождать «прошло». 2. Консоль облака → Compute Cloud: машина должна быть `Running`; если `Stopped` — запустить. 3. На машине: `sudo docker ps` — должны быть `uchetkin-caddy`, `uchetkin-api`, `uchetkin-web` (и `uchetkin-postgres` в dev). Чего-то нет — `cd /opt/uchetkin && sudo docker compose up -d`. 4. Не помогло — `sudo docker logs --tail 100 uchetkin-api`, последние строки с `"level":50` и есть причина. 5. Если упало после выкладки — откат по `docs/release.md` |
| 🔴 **Много ошибок сервера (5xx)** | За 5 минут больше 2 % запросов завершились ошибкой сервера (считается при ≥ 20 запросах) | 1. `sudo docker ps` — контейнер `uchetkin-api` должен быть `healthy`; если `Restarting` — `sudo docker logs --tail 100 uchetkin-api`. 2. Cloud Logging → группа контура → фильтр `"statusCode":5` — какой запрос падает. 3. Ошибки только после выкладки — откат (`docs/release.md`). 4. В dev база в контейнере: `sudo docker logs --tail 50 uchetkin-postgres` |
| 🔴 **Диск машины почти заполнен** | Корневой диск занят на 80 % и больше. Место съедают журналы Docker и старые образы | 1. `df -h /` и `sudo du -sh /var/lib/docker /var/lib/uchetkin /var/log`. 2. `sudo docker system prune -f` — убирает старые образы и контейнеры выкладок (данные не трогает). 3. Журналы Docker ограничены 5 × 50 МБ на контейнер; если `/var/log` велик — `sudo journalctl --vacuum-size=200M`. 4. Не помогает — увеличить диск: `infra/*.tfvars`, `vm_disk_size`, затем `terraform apply` (машина перезагрузится) |
| 🔴 **Резервная копия базы устарела** | Последняя удачная копия сделана больше 26 часов назад, или ни одной ещё не было | 1. `sudo systemctl start uchetkin-backup` и `sudo journalctl -u uchetkin-backup -n 30` — причина в последних строках (нет доступа к бакету, база не отвечает). 2. `sudo systemctl status uchetkin-backup.timer` — таймер должен быть `active (waiting)`; если нет — `sudo systemctl enable --now uchetkin-backup.timer`. 3. Пока копий нет, база без страховки: в prod остаются автоматические копии кластера, в dev — ничего |
| 🔴 **Сертификат скоро истечёт** | До конца сертификата HTTPS меньше 14 дней. Caddy продлевает его сам за 30 дней — раз не продлил, ему что-то мешает | 1. `sudo docker logs uchetkin-caddy 2>&1 \| grep -i acme \| tail -20` — причина. 2. Обычно: закрыт порт 80 или 443 снаружи, либо A-запись домена больше не ведёт на машину (`terraform output app_external_ip`). 3. Поправить и `sudo docker restart uchetkin-caddy`. Если сертификат уже истёк — браузеры перестанут открывать систему |
| 🔴 **Машина не присылает служебные метрики** | 20 минут нет метрик `uchetkin.*`. Если при этом система работает — остановлен агент мониторинга или таймер `uchetkin-status`; если не работает — см. «Система недоступна» | 1. `sudo systemctl status uchetkin-status.timer`; `sudo systemctl start uchetkin-status` и прочитать вывод. 2. `sudo docker ps \| grep unified-agent`; нет — `cd /opt/uchetkin && sudo docker compose -f compose.platform.yml up -d`. 3. `sudo docker logs --tail 30 unified-agent` — ошибки конфигурации |
| 🟢 **… — прошло** | Проблема, о которой писали, ушла сама или после действий | Ничего. Если приходит парами «недоступна / прошло» несколько раз в день — система перезапускается, смотреть журнал `uchetkin-api` |

Пороги (2 минуты, 2 %, 80 %, 26 часов, 14 дней, напоминание через 6 часов)
заданы переменной `alert_thresholds` в `infra/variables.tf`.

### Как включить каналы

Сторож уже работает и пишет каждое оповещение в Cloud Logging. Чтобы оно
приходило людям, нужно один раз заполнить два секрета в консоли облака
(Lockbox), значения в репозиторий не попадают:

1. **Telegram.** Создать бота через @BotFather (команда `/newbot`), получить
   токен. Написать боту любое сообщение с телефона, на который должны
   приходить оповещения (или добавить бота в группу), и узнать `chat_id`:
   открыть `https://api.telegram.org/bot<токен>/getUpdates` — поле `chat.id`.
   В Lockbox → секрет `uchetkin-<контур>-alerts` → новая версия с записями
   `telegram_bot_token` и `telegram_chat_id`.
2. **Почта.** Lockbox → секрет `uchetkin-<контур>-smtp` → записи `host`,
   `port` (465 или 587), `user`, `password`, `from`. Адрес получателя —
   переменная `alert_email` в `infra/<контур>.tfvars`, затем `terraform apply`.
3. **Проверить, не дожидаясь беды:**

   ```bash
   yc serverless function invoke uchetkin-<контур>-watchdog -d '{"test": true}'
   ```

   В ответе `delivery` покажет по каждому каналу «отправлено» или причину.

Секреты сторож читает при каждом запуске — после заполнения ничего
перезапускать не нужно.

## Резервные копии

| Копия | Где | Как часто | Сколько хранится | Кто делает |
| --- | --- | --- | --- | --- |
| Автоматическая копия кластера Managed PostgreSQL + журнал для восстановления на момент времени | облако, кластер → Резервные копии | ежедневно, окно 20:00 UTC (01:00 по Екатеринбургу) | 14 дней | облако (`infra/postgres.tf`), только prod |
| `pg_dump` ежедневный | бакет `uchetkin-<контур>-ops`, `pg/daily/uchetkin-<дата>.dump` | ежедневно 02:30 по Екатеринбургу | 14 дней | таймер `uchetkin-backup` на ВМ |
| `pg_dump` еженедельный | тот же бакет, `pg/weekly/` | воскресенье, вместе с ежедневным | год (через 30 дней уходит в холодное хранилище) | тот же таймер |
| Фото актов, записи разговоров | бакеты `-acts`, `-calls` | сразу при загрузке | без удаления, версионирование включено: перезаписанный или удалённый объект остаётся прежней версией | приложение; хранение — `infra/storage.tf` |
| Снимок диска ВМ | облако → Снимки | воскресенье 21:00 UTC | 4 последних | облако (`infra/compute.tf`), только prod |

Копии в бакете зашифрованы ключом KMS контура, машина может только дописывать
(роль `storage.uploader`): стереть копию с машины нельзя даже при взломе.
Возраст последней удачной копии виден на дашборде машины и сторожит сторож.

## Восстановление базы

Три ситуации, от простой к тяжёлой. Время — по учениям 18.09.2026 (протокол
ниже); в prod данные больше, но порядок величин тот же: база за первый год —
десятки мегабайт.

### А. Откатить данные на момент времени (prod, испорчены данные, кластер жив)

Например, ошибочный импорт затёр клиентов. Managed PostgreSQL умеет
восстановить кластер на любую секунду за последние 14 дней **в новый кластер**.

1. Консоль → Managed Service for PostgreSQL → кластер → Резервные копии →
   у нужной копии «Восстановить кластер», указать момент времени. Или CLI:

   ```bash
   yc managed-postgresql backup list --cluster-name uchetkin-prod-pg
   yc managed-postgresql cluster restore --backup-id <id> --time <RFC3339> \
     --name uchetkin-prod-pg-restore --environment production \
     --network-id <сеть контура> --host zone-id=ru-central1-a,subnet-id=<подсеть> \
     --resource-preset b2.medium --disk-type network-ssd --disk-size 20 \
     --security-group-ids <группа sg-db>
   ```

   Ждать `RUNNING` — **около 10 минут** (на учениях создание кластера того же
   класса заняло 9 мин 50 с).
2. Убедиться, что в новом кластере данные те: подключиться с машины
   (`docker run --rm -e PGPASSWORD=… postgres:16-alpine psql -h <host нового> -p 6432 -U uchetkin_app -d uchetkin`)
   и проверить заявку или клиента, из-за которых начали.
3. Переключить приложение: Lockbox → секрет `uchetkin-prod-db` → новая версия,
   запись `host` — FQDN хоста нового кластера. Затем на машине
   `cd /opt/uchetkin && sudo docker compose restart api worker` и `curl
   http://127.0.0.1:3000/health` — должно быть `"db":"ok"`. **1–2 минуты.**
4. Привести Terraform в соответствие (иначе следующий `apply` вернёт старый
   хост): `terraform state rm yandex_mdb_postgresql_cluster.main[0]`,
   `terraform import yandex_mdb_postgresql_cluster.main[0] <id нового>`,
   переименовать новый кластер в `uchetkin-prod-pg` после удаления старого.
   Старый кластер удалить, когда новый поработал день: `deletion_protection`
   сначала снять в консоли.

### Б. Восстановить из `pg_dump` (любой контур; кластер жив или новый)

1. Взять дамп из бакета — с машины, по её сервисному аккаунту:

   ```bash
   TOKEN=$(curl -sfH 'Metadata-Flavor: Google' \
     http://169.254.169.254/computeMetadata/v1/instance/service-accounts/default/token | jq -re .access_token)
   . /etc/uchetkin/app.env
   curl -sf -H "Authorization: Bearer $TOKEN" -o /tmp/restore.dump \
     "https://storage.yandexcloud.net/$OPS_BUCKET/pg/daily/uchetkin-<дата>.dump"
   ```

   Список копий — консоль → Object Storage → бакет `ops`. Скачивание —
   секунды.
2. Восстановить **в пустую базу**. В dev (контейнер):

   ```bash
   sudo docker compose -f /opt/uchetkin/compose.yml stop api worker
   sudo docker exec -i uchetkin-postgres pg_restore -U uchetkin_app -d uchetkin \
     --clean --if-exists --no-owner --no-privileges < /tmp/restore.dump
   sudo docker compose -f /opt/uchetkin/compose.yml start api worker
   ```

   В prod (Managed PostgreSQL, порт 6432 — прямой 5432 снаружи закрыт):

   ```bash
   sudo docker run --rm -i -e PGPASSWORD='<пароль из Lockbox uchetkin-prod-db>' postgres:16-alpine \
     pg_restore -h <host кластера> -p 6432 -U uchetkin_app -d uchetkin \
     --clean --if-exists --no-owner --no-privileges < /tmp/restore.dump
   ```

   На учениях `pg_restore` 29 таблиц и 14 тысяч строк занял **1,7 с**.
3. Проверить: `curl http://127.0.0.1:3000/health` → `"db":"ok"`, войти в
   систему, открыть список заявок. Всё вместе — **до 5 минут** с момента, как
   дамп на машине.

Всё, что сделано в системе после момента копии, потеряно: ежедневный дамп —
это до суток работы. Для prod поэтому первым выбором остаётся вариант А.

### В. Потеряна машина целиком

1. `terraform apply` из `infra/` пересоздаёт машину и раскладывает платформу
   (cloud-init: Docker, агент, таймеры) — **около 5 минут**.
2. Выкладка приложения — «Выкладка в prod» в GitHub Actions с последним
   тегом (`docs/release.md`) — **около 5 минут**.
3. База в prod живёт отдельно и не пострадала. В dev — вариант Б.

Итого для prod — порядка 15 минут до работоспособности, из них руками —
два запуска.
