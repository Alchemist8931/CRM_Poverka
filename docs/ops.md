# Эксплуатация: оповещения, журналы, резервные копии, восстановление

Пункт плана `cloud-ops`. Страница для того, кто получил оповещение и должен
понять, что случилось и что делать, — без администратора под рукой. Как это
описано кодом — `infra/README.md`, раздел «Эксплуатация».

## Что и где смотреть

| Что | Где | Зачем |
| --- | --- | --- |
| Оповещения | пока — журнал `watchdog/alerts.json` в бакете `ops` и Cloud Logging; Telegram-бот и почта — после заполнения секретов (см. «Каналы сейчас: заглушка») | узнать о проблеме, не заглядывая никуда |
| Дашборды | консоль облака → Monitoring → Дашборды → `uchetkin-<контур>-vm`, `-http`, `-postgres` (prod) | посмотреть, что происходило с машиной, запросами и базой |
| Журналы приложения | консоль облака → Cloud Logging → группа `uchetkin-<контур>-app` | найти ошибку по времени или по номеру заявки; хранятся 30 дней |
| Журнал сторожа | та же группа, ресурс `serverless.function` | каждая проверка (раз в минуту) и каждое отправленное оповещение с полным текстом |
| Резервные копии базы | консоль → Object Storage → бакет `uchetkin-<контур>-ops`, папки `pg/daily` (14 дней) и `pg/weekly` (год) | восстановить базу |
| Автоматические копии Managed PostgreSQL (prod) | консоль → Managed Service for PostgreSQL → кластер → Резервные копии | восстановить кластер целиком на момент времени, 14 дней |
| Снимки диска ВМ (prod) | консоль → Compute Cloud → Снимки | вернуть машину, если сломалась она сама |

Сторож проверяет систему **снаружи** облака раз в минуту: открывает `/health`,
читает служебные метрики машины и счётчики Caddy, при включённом TLS проверяет
сертификат. Об одной проблеме он пишет один раз, потом напоминает каждые
6 часов, пока она не пройдёт, и пишет «прошло», когда всё вернулось.

## Оповещения: что значит и что делать

Все команды ниже выполняются на машине контура (`crm-uchetkin-prod` в dev):
консоль облака → Compute Cloud → машина → «Серийная консоль», либо SSH, если
он открыт. Команды начинаются с `sudo`.

| Оповещение | Что значит | Что делать по порядку |
| --- | --- | --- |
| 🔴 **Система недоступна** | `/health` не отвечает две минуты подряд. Либо остановилось приложение, либо машина, либо сеть до неё | 1. Открыть систему в браузере: если открывается — ложная тревога сети, подождать «прошло». 2. Консоль облака → Compute Cloud: машина должна быть `Running`; если `Stopped` — запустить. 3. На машине: `sudo docker ps` — должны быть `uchetkin-caddy`, `uchetkin-api`, `uchetkin-web` (и `uchetkin-postgres` в dev). Чего-то нет — `cd /opt/uchetkin && sudo docker compose up -d`. 4. Не помогло — `sudo docker logs --tail 100 uchetkin-api`, последние строки с `"level":50` и есть причина. 5. Если упало после выкладки — откат по `docs/release.md` |
| 🔴 **Много ошибок сервера (5xx)** | За 5 минут больше 2 % запросов завершились ошибкой сервера (считается при ≥ 20 запросах) | 1. `sudo docker ps` — контейнер `uchetkin-api` должен быть `healthy`; если `Restarting` — `sudo docker logs --tail 100 uchetkin-api`. 2. Cloud Logging → группа контура → фильтр `"statusCode":5` — какой запрос падает. 3. Ошибки только после выкладки — откат (`docs/release.md`). 4. В dev база в контейнере: `sudo docker logs --tail 50 uchetkin-postgres` |
| 🔴 **Диск машины почти заполнен** | Корневой диск занят на 80 % и больше. Место съедают журналы Docker и старые образы | 1. `df -h /` и `sudo du -sh /var/lib/docker /var/lib/uchetkin /var/log`. 2. `sudo docker system prune -f` — убирает старые образы и контейнеры выкладок (данные не трогает). 3. Журналы Docker ограничены 5 × 50 МБ на контейнер; если `/var/log` велик — `sudo journalctl --vacuum-size=200M`. 4. Не помогает — увеличить диск: `infra/*.tfvars`, `vm_disk_size`, затем `terraform apply` (машина перезагрузится) |
| 🔴 **Резервная копия базы устарела** | Последняя удачная копия сделана больше 26 часов назад, или ни одной ещё не было | 1. `sudo systemctl start uchetkin-backup` и `sudo journalctl -u uchetkin-backup -n 30` — причина в последних строках (нет доступа к бакету, база не отвечает). 2. `sudo systemctl status uchetkin-backup.timer` — таймер должен быть `active (waiting)`; если нет — `sudo systemctl enable --now uchetkin-backup.timer`. 3. Пока копий нет, база без страховки: в prod остаются автоматические копии кластера, в dev — ничего |
| 🔴 **Сертификат скоро истечёт** | До конца сертификата HTTPS меньше 14 дней. Caddy продлевает его сам за 30 дней — раз не продлил, ему что-то мешает | 1. `sudo docker logs uchetkin-caddy 2>&1 \| grep -i acme \| tail -20` — причина. 2. Обычно: закрыт порт 80 или 443 снаружи, либо A-запись домена больше не ведёт на машину (`terraform output app_external_ip`). 3. Поправить и `sudo docker restart uchetkin-caddy`. Если сертификат уже истёк — браузеры перестанут открывать систему |
| 🔴 **Машина не присылает служебные метрики** | 20 минут нет метрик `uchetkin.*`. Если при этом система работает — остановлен агент мониторинга или таймер `uchetkin-status`; если не работает — см. «Система недоступна» | 1. `sudo systemctl status uchetkin-status.timer`; `sudo systemctl start uchetkin-status` и прочитать вывод. 2. `sudo docker ps \| grep unified-agent`; нет — `cd /opt/uchetkin && sudo docker compose -f compose.platform.yml up -d`. 3. `sudo docker logs --tail 30 unified-agent` — ошибки конфигурации |
| 🟢 **… — прошло** | Проблема, о которой писали, ушла сама или после действий | Ничего. Если приходит парами «недоступна / прошло» несколько раз в день — система перезапускается, смотреть журнал `uchetkin-api` |

Пороги (2 минуты, 2 %, 80 %, 26 часов, 14 дней, напоминание через 6 часов)
заданы переменной `alert_thresholds` в `infra/variables.tf`.

### Каналы сейчас: заглушка

По решению владельца от 18.09.2026 Telegram и почта подключаются позднее.
До этого сторож работает полностью, а оповещения доставляет в два места,
которые не требуют настройки:

- **Cloud Logging** — группа `uchetkin-<контур>-app`, ресурс
  `serverless.function`, записи уровня `WARN` с полем `event: alert`;
- **журнал последних оповещений** — файл `watchdog/alerts.json` в бакете
  `uchetkin-<контур>-ops` (консоль → Object Storage → бакет → `watchdog/`),
  последние 50 оповещений с текстом и результатом доставки по каждому каналу.

Проверено 18.09.2026 в 12:03 по Екатеринбургу: `yc serverless function invoke
uchetkin-dev-watchdog -d '{"test": true}'` ответил

```
telegram: канал не настроен (секрет alerts пуст)
email: адрес не задан (alert_email пуст)
журнал: записано в s3://uchetkin-dev-ops/watchdog/alerts.json
```

а в `watchdog/alerts.json` появилась запись с текстом «✅ Учёткин (dev):
проверка оповещений. Если вы это читаете — канал работает. 18.09, 12:03.»
и результатом доставки по каждому каналу. Так же будут выглядеть настоящие
тревоги, пока каналы не подключены.

### Как включить каналы

Чтобы оповещение приходило людям, нужно один раз заполнить два секрета в
консоли облака (Lockbox), значения в репозиторий не попадают; код сторожа
менять не нужно:

1. **Telegram.** Создать бота через @BotFather (команда `/newbot`), получить
   токен. Написать боту любое сообщение с телефона, на который должны
   приходить оповещения (или добавить бота в группу), и узнать `chat_id`:
   открыть `https://api.telegram.org/bot<токен>/getUpdates` — поле `chat.id`.
   В Lockbox → секрет `uchetkin-<контур>-alerts` → новая версия с записями
   `telegram_bot_token` и `telegram_chat_id`.
2. **Почта.** Lockbox → секрет `uchetkin-<контур>-smtp` → записи `host`,
   `port` (465 или 587), `user`, `password`, `from`. Адрес получателя —
   переменная `alert_email` в `infra/<контур>.tfvars`, затем `terraform apply`.
3. **Проверить, не дожидаясь беды:**

   ```bash
   yc serverless function invoke uchetkin-<контур>-watchdog -d '{"test": true}'
   ```

   В ответе `delivery` покажет по каждому каналу «отправлено» или причину.

Секреты сторож читает при каждом запуске — после заполнения ничего
перезапускать не нужно.

### Как выглядит оповещение

Текст из журнала сторожа на учебной остановке приложения в dev 18.09.2026
(контейнер `uchetkin-api` остановлен на 3,5 минуты; каналы доставки ещё не
заполнены, поэтому в `delivery` — «канал не настроен»):

```text
🔴 Учёткин (dev): Система недоступна

Проверка http://84.201.139.101/health не проходит уже 2 минуты (с 18.09, 08:09): код 502.

Что делать: Откройте http://84.201.139.101. Не открывается — в консоли облака проверьте, что машина crm-uchetkin-prod запущена, затем docs/ops.md, «Система недоступна».

18.09, 08:09, сторож напомнит через 6 ч, если не пройдёт.
```

Запись в журнале (Cloud Logging, ресурс `serverless.function`, 03:09:32 UTC):

```json
{"event":"alert","subject":"Учёткин (dev): Система недоступна",
 "delivery":["telegram: канал не настроен (секрет alerts пуст)","email: адрес не задан (alert_email пуст)"]}
```

Время в тексте — по Екатеринбургу (переменная `timezone`), адрес проверки —
пока статический IP по `http`: TLS в dev выключен до появления A-записи.

## Резервные копии

| Копия | Где | Как часто | Сколько хранится | Кто делает |
| --- | --- | --- | --- | --- |
| Автоматическая копия кластера Managed PostgreSQL + журнал для восстановления на момент времени | облако, кластер → Резервные копии | ежедневно, окно 20:00 UTC (01:00 по Екатеринбургу) | 14 дней | облако (`infra/postgres.tf`), только prod |
| `pg_dump` ежедневный | бакет `uchetkin-<контур>-ops`, `pg/daily/uchetkin-<дата>.dump` | ежедневно 02:30 по Екатеринбургу | 14 дней | таймер `uchetkin-backup` на ВМ |
| `pg_dump` еженедельный | тот же бакет, `pg/weekly/` | воскресенье, вместе с ежедневным | год (через 30 дней уходит в холодное хранилище) | тот же таймер |
| Фото актов, записи разговоров | бакеты `-acts`, `-calls` | сразу при загрузке | без удаления, версионирование включено: перезаписанный или удалённый объект остаётся прежней версией | приложение; хранение — `infra/storage.tf` |
| Снимок диска ВМ | облако → Снимки | воскресенье 21:00 UTC | 4 последних | облако (`infra/compute.tf`), только prod |

Копии в бакете зашифрованы ключом KMS контура, машина может только дописывать
(роль `storage.uploader`): стереть копию с машины нельзя даже при взломе.
Возраст последней удачной копии виден на дашборде машины и сторожит сторож.

## Восстановление базы

Три ситуации, от простой к тяжёлой. Время — по учениям 18.09.2026 (протокол
ниже); в prod данные больше, но порядок величин тот же: база за первый год —
десятки мегабайт.

### А. Откатить данные на момент времени (prod, испорчены данные, кластер жив)

Например, ошибочный импорт затёр клиентов. Managed PostgreSQL умеет
восстановить кластер на любую секунду за последние 14 дней **в новый кластер**.

1. Консоль → Managed Service for PostgreSQL → кластер → Резервные копии →
   у нужной копии «Восстановить кластер», указать момент времени. Или CLI:

   ```bash
   yc managed-postgresql backup list --cluster-name uchetkin-prod-pg
   yc managed-postgresql cluster restore --backup-id <id> --time <RFC3339> \
     --name uchetkin-prod-pg-restore --environment production \
     --network-id <сеть контура> --host zone-id=ru-central1-a,subnet-id=<подсеть> \
     --resource-preset b2.medium --disk-type network-ssd --disk-size 20 \
     --security-group-ids <группа sg-db>
   ```

   Ждать `RUNNING` — **около 10 минут** (на учениях создание кластера того же
   класса заняло 9 мин 50 с).
2. Убедиться, что в новом кластере данные те: подключиться с машины
   (`docker run --rm -e PGPASSWORD=… postgres:16-alpine psql -h <host нового> -p 6432 -U uchetkin_app -d uchetkin`)
   и проверить заявку или клиента, из-за которых начали.
3. Переключить приложение: Lockbox → секрет `uchetkin-prod-db` → новая версия,
   запись `host` — FQDN хоста нового кластера. Затем на машине
   `cd /opt/uchetkin && sudo docker compose restart api worker` и `curl
   http://127.0.0.1:3000/health` — должно быть `"db":"ok"`. **1–2 минуты.**
4. Привести Terraform в соответствие (иначе следующий `apply` вернёт старый
   хост): `terraform state rm yandex_mdb_postgresql_cluster.main[0]`,
   `terraform import yandex_mdb_postgresql_cluster.main[0] <id нового>`,
   переименовать новый кластер в `uchetkin-prod-pg` после удаления старого.
   Старый кластер удалить, когда новый поработал день: `deletion_protection`
   сначала снять в консоли.

### Б. Восстановить из `pg_dump` (любой контур; кластер жив или новый)

1. Взять дамп из бакета — с машины, по её сервисному аккаунту:

   ```bash
   TOKEN=$(curl -sfH 'Metadata-Flavor: Google' \
     http://169.254.169.254/computeMetadata/v1/instance/service-accounts/default/token | jq -re .access_token)
   . /etc/uchetkin/app.env
   curl -sf -H "Authorization: Bearer $TOKEN" -o /tmp/restore.dump \
     "https://storage.yandexcloud.net/$OPS_BUCKET/pg/daily/uchetkin-<дата>.dump"
   ```

   Список копий — консоль → Object Storage → бакет `ops`. Скачивание —
   секунды.
2. Восстановить **в пустую базу**. В dev (контейнер):

   ```bash
   sudo docker compose -f /opt/uchetkin/compose.yml stop api worker
   sudo docker exec -i uchetkin-postgres pg_restore -U uchetkin_app -d uchetkin \
     --clean --if-exists --no-owner --no-privileges < /tmp/restore.dump
   sudo docker compose -f /opt/uchetkin/compose.yml start api worker
   ```

   В prod (Managed PostgreSQL, порт 6432 — прямой 5432 снаружи закрыт):

   ```bash
   sudo docker run --rm -i -e PGPASSWORD='<пароль из Lockbox uchetkin-prod-db>' postgres:16-alpine \
     pg_restore -h <host кластера> -p 6432 -U uchetkin_app -d uchetkin \
     --clean --if-exists --no-owner --no-privileges < /tmp/restore.dump
   ```

   На учениях `pg_restore` 29 таблиц и 14 тысяч строк занял **1,7 с**.
3. Проверить: `curl http://127.0.0.1:3000/health` → `"db":"ok"`, войти в
   систему, открыть список заявок. Всё вместе — **до 5 минут** с момента, как
   дамп на машине.

Всё, что сделано в системе после момента копии, потеряно: ежедневный дамп —
это до суток работы. Для prod поэтому первым выбором остаётся вариант А.

### В. Потеряна машина целиком

1. `terraform apply` из `infra/` пересоздаёт машину и раскладывает платформу
   (cloud-init: Docker, агент, таймеры) — **около 5 минут**.
2. Выкладка приложения — «Выкладка в prod» в GitHub Actions с последним
   тегом (`docs/release.md`) — **около 5 минут**.
3. База в prod живёт отдельно и не пострадала. В dev — вариант Б.
4. Новая машина к шлюзу агента не подключена: агент в cloud-init не входит.
   Подключить заново — раздел «Машина и шлюз агента» ниже.

Итого для prod — порядка 15 минут до работоспособности, из них руками —
два запуска.

## Рабочий контур (с 18.09.2026; на боевом домене с 20.09.2026)

Решение владельца 18.09.2026 (пункт плана `live-ip`): система запущена в
работу на dev-контуре по адресу `http://84.201.139.101` — без домена и TLS.
В тот же день (пункт `live-tls`) включён HTTPS на временном имени
`https://84-201-139-101.sslip.io`. 20.09.2026 (пункт `cloud-domain`) система
переведена на боевой домен `https://uchetkin.ru`: сертификат Let's Encrypt
получил и продлевает Caddy на машине, старый адрес и временное имя отвечают
редиректом. Отдельный prod — после запуска (пункт `cloud-prod`). Пока так,
dev и рабочий контур — одна и та же машина, и обращаться с ней нужно как с
prod.

| Что | Как |
| --- | --- |
| Адрес | `https://uchetkin.ru` (`app_domain` и `tls_enabled = true` в `infra/dev.tfvars`). В `app.env` `PUBLIC_BASE_URL`, `API_BASE_URL`, `WEBHOOK_BASE_URL` смотрят на него, `COOKIE_DOMAIN` — имя; Terraform считает их от `tls_enabled` (`infra/locals.tf`, `site_origin`). Cookie с `Secure`, строки `SESSION_COOKIE_SECURE` в `app.env` нет. Со старых `http://84.201.139.101` и `84-201-139-101.sslip.io` и с `www` Caddy отвечает 301 на домен (`legacy_redirect_from`, файл `/etc/uchetkin/caddy.d/legacy.caddy`) — голый адрес и временное имя убрать не раньше 20.10.2026, `www` остаётся |
| Сертификат | на `uchetkin.ru` и `www.uchetkin.ru` выпущены 20.09.2026 на 90 дней (до 19.12.2026), продление — Caddy сам (журнал `docker compose logs caddy`, строки `tls.obtain`/`tls.renew`); дни до конца видны в `uchetkin-status` («сертификат N дн.»). Сертификат временного имени остаётся в томе `caddy_data` ради редиректа и уйдёт вместе с ним |
| Учётные записи | `owner` и `berdinskikh` — полный доступ; временные пароли в секрете Lockbox `uchetkin-handover` каталога `default`: владелец читает в консоли, передаёт заказчице, секрет удаляет. Остальных сотрудников заводит заказчица на экране «Сотрудники» |
| Данные | демо-набор убран скриптом `server/scripts/purge-demo.sql`, остались справочники из книги `req-refs`. **Не запускать** `npm run seed` и `uat-stand`: они стирают и перезаливают базу |
| Автотесты | `.github/workflows/uat.yml` — только по кнопке, расписание и запуск на push сняты. На рабочем контуре не гонять: сценарии заводят сотрудников, заявки и маршруты |
| Копии | таймер `uchetkin-backup` (02:30 по Екатеринбургу) → бакет `uchetkin-dev-ops`, `pg/daily`. Перед любым вмешательством в базу — `sudo systemctl start uchetkin-backup` и строка «→ s3://…» в `sudo journalctl -u uchetkin-backup -n 3` |
| Выкладка | руками на машине — `docs/release.md`, «Выкладка руками на рабочем контуре»: копия, миграции, перезапуск — в этом порядке |
| Сторож | проверяет `https://uchetkin.ru/health` (`APP_URL` функции — из того же `site_origin`) |
| Потеря машины | база в томе `pgdata` на диске ВМ; восстановление — раздел «В. Потеряна машина целиком». После пересоздания cloud-init перепишет `app.env`, `caddy.env` и `caddy.d/legacy.caddy` с доменом сам; сертификат Caddy получит заново (том `caddy_data` уходит вместе с машиной) |

## Включение телефонии (пункт `novofon-live`)

Телефония включается ключами, а не выкладкой: код приёмника, карточки и звонка
из карточки на контуре уже есть (пункт `int-novofon`, разбор — `docs/api.md`,
раздел «Связь»). Пока в секрете Lockbox `uchetkin-dev-novofon` пусто, приёмник
уведомлений отвечает 503, кнопка «Позвонить» — «телефония не подключена», и это
рабочее состояние, а не поломка: заявки принимаются по телефону как раньше.

### Что читается из секрета

Секрет заводится Terraform пустым (`infra/variables.tf`,
`lockbox_external_secrets`), значения вносит человек. Имена записей и переменные,
в которые они попадают при старте API (`server/src/secrets.ts`, `novofonEnvFrom`):

| Запись секрета | Переменная | Откуда берётся в кабинете | Без неё |
| --- | --- | --- | --- |
| `webhook_secret` | `NOVOFON_WEBHOOK_SECRET` | придумывается здесь: 32 случайных знака, тем же текстом идёт в адрес приёмника в кабинете | приёмник отвечает 503, событий звонков нет |
| `access_token` | `NOVOFON_ACCESS_TOKEN` | «Пользователи АТС → Администратор → API», строка Secret | `canCall()` ложный: звонок из карточки и сверка записей не работают |
| `virtual_number` | `NOVOFON_VIRTUAL_NUMBER` | «Виртуальные номера», номер в виде `73432269924` (E.164 без плюса) | то же: АТС не знает, каким номером звонить клиенту |
| `group_id` | `NOVOFON_GROUP_ID` | «Телефония → Группы», идентификатор группы операторов | отметка «на паузе» остаётся в CRM и не уходит в АТС (входящие всё равно распределяет приёмник `routing`) |
| `allowed_ips` | `NOVOFON_ALLOWED_IPS` | адрес, с которого АТС шлёт уведомления: `37.139.38.215` | проверки адреса нет: приёмник пускает всех, у кого сходится секрет |

Заданное в `app.env` сильнее секрета и из Lockbox не перетирается. Записи с
чужими именами пропускаются: подставлять «первую попавшуюся» под секрет
приёмника нельзя — под него уехал бы ключ API.

### Порядок включения

1. Придумать секрет приёмника (32 знака) и **сначала** положить его в Lockbox,
   и только потом вписывать в кабинет: обратный порядок означает открытый адрес,
   который АТС уже знает, а система ещё нет.

   Консоль → Lockbox → `uchetkin-dev-novofon` → «Создать версию»: записи из
   таблицы выше. Из песочницы то же делает `yc` (профиль `crm-deploy`)
   командой `lockbox secret add-version`. Версия создаётся целиком: записи,
   которых в новой версии нет, пропадают — вносить надо все сразу.
2. Шаги в кабинете Новофон — памятка владельцу (файл чата
   «Новофон — подключение номера и АТС»): тариф, номер, два пользователя АТС с
   внутренними номерами, равными полю «Внутренний номер» на экране «Сотрудники»
   в CRM, ключ API, список адресов API (`84.201.139.101`), уведомления и
   входящий сценарий с шагом «Интерактивная обработка вызова».

   Адреса, которые вписываются в кабинет, система считает сама от
   `PUBLIC_BASE_URL` и показывает руководителю на экране «Сотрудники» (блок
   «Телефония») и в `GET /api/calls/settings`; их же печатает API при старте.
   Вписывать руками собранный адрес не надо — в нём легко ошибиться секретом.
3. Перезапустить API, чтобы он перечитал Lockbox:
   `sudo docker compose -f /opt/uchetkin/compose.yml restart api`. В журнале
   (`docker compose logs api | head -40`) появятся обе строки адресов с секретом.
4. Связать учётные записи с сотрудниками АТС: экран «Сотрудники» → «Телефония»
   → «Подтянуть из АТС». Сверка идёт по внутреннему номеру, расхождения
   показываются, а связь ставится по кнопке — молча система ничего не правит.
   Готовность видна там же: «Приём событий: включён», «обращения к АТС:
   включены» и состояние «совпало» у обоих сотрудников.

### Как отключить

Создать пустую версию секрета (или снять записи `access_token` и
`webhook_secret`) и перезапустить API. Приёмник снова отвечает 503, кнопка
«Позвонить» — отказом, всё остальное в системе работает как прежде. В кабинете
Новофона при этом полезно снять уведомления: иначе АТС будет стучаться в
закрытый приёмник и копить свои ошибки доставки. Строки в `calls` и события в
`call_events` остаются — они история, а не настройка.

### Что меняется при переезде на prod

Адреса приёмников считаются от `PUBLIC_BASE_URL`, а он на prod другой. В день
переезда (раздел «Переезд рабочего контура в prod») к списку работ добавляются
три строки:

- секрет `uchetkin-prod-novofon` наполняется теми же записями (Lockbox
  копированием версий между каталогами не умеет — вносить заново);
- в кабинете Новофон меняются адрес уведомлений и адрес шага «Интерактивная
  обработка вызова» — их берут из `GET /api/calls/settings` уже на prod;
- в «Правила и настройки безопасности → API» вписывается адрес prod-машины,
  старый убирается после того, как круг звонков проверен.

Связь сотрудников с АТС (`staff.novofon_employee_id`) переезжает вместе с базой:
заново подтягивать её не нужно, если в кабинете не менялись пользователи АТС.

## Переезд рабочего контура в prod (пункт `cloud-prod`)

Отдельный prod-контур по плану запуска (`docs/launch.md`, «Что появится после
пилота») поднимается после пилота: он платный с первого дня (≈ 8,5–8,9 тыс. ₽
в месяц с НДС, расчёт — `infra/README.md`, «Сколько это стоит»), а рабочая
система уже живёт на dev-машине. Дату и каталог называет владелец. Всё, что не
зависит от даты, сделано 18.09.2026 (`infra/README.md`, «Что применено»).

### Чем контуры различаются

| | dev (рабочий с 18.09.2026) | prod (после apply) |
| --- | --- | --- |
| Каталог облака | `default` (`b1giq117a18cpiolfife`) | `crm-prod`, заводит владелец; идентификатор — в `infra/prod.tfvars` |
| Адрес | `https://uchetkin.ru` (`cloud-domain`, с 20.09.2026), со старого адреса, временного имени и `www` — редирект | `https://<адрес>.sslip.io`, HTTPS с первого дня; домен переезжает вместе с системой (`app_domain` в `prod.tfvars`) |
| Машина | `crm-uchetkin-prod`, принята в Terraform как есть | `uchetkin-prod-app`, создаётся Terraform целиком, cloud-init раскладывает всё сам |
| База | контейнер PostgreSQL на машине, том `pgdata` | Managed PostgreSQL `uchetkin-prod-pg` (b2.medium, 20 ГБ, порт 6432, только TLS), защита от удаления |
| Копии | `pg_dump` таймером в `uchetkin-dev-ops` — единственная копия | те же дампы в `uchetkin-prod-ops` **плюс** автоматические копии кластера 14 дней и восстановление на момент времени, снимки диска ВМ раз в неделю |
| Секреты | Lockbox `uchetkin-dev-*` | Lockbox `uchetkin-prod-*`, защита от удаления; внешние (`novofon`, `arshin`, `maps`, `smtp`, `alerts`) заполняются заново в консоли |
| Выкладка | руками на машине, образы `:manual` (`docs/release.md`) | только «Выкладка в prod» в GitHub Actions: тег, подтверждение, сборка в реестр prod, миграции, `/health` |
| Шлюз агента | подключена (строка «CRM Учеткин») | подключается **только отдельной строкой и только с согласия владельца**; без согласия — работа только через выкладку |

### Порядок переезда (окно 30 минут вечером)

1. **Поднять prod** — `infra/README.md`, «Порядок применения», шаг 4 (два
   шага: адрес, затем всё остальное с настоящим именем). Повторный `plan` —
   «No changes». Модуль `infra/dashboards` — с `backend-prod.hcl`.
2. **Выложить текущий тег** через «Выкладка в prod». Проверить `/health` по
   имени снаружи — `200`, войти не во что: база пустая, учёток нет.
3. **Заморозить старый контур**: предупредить сотрудников, на машине
   `sudo docker compose stop api` — приём заявок остановлен; снять копию
   `sudo systemctl start uchetkin-backup` и дождаться строки «→ s3://…» в
   `journalctl -u uchetkin-backup`.
4. **Перенести базу** в кластер (`pg_restore` через 6432, пароль из Lockbox
   `uchetkin-prod-db`, `sslmode=verify-full` с `server/certs/yandex-cloud-ca.pem`) —
   тем же приёмом, что в «Б. Восстановить из `pg_dump`». На учениях 18.09.2026
   восстановление заняло 1,7 с. Учётные записи `owner`, `berdinskikh` и
   заведённые заказчицей сотрудники переезжают вместе с базой; `init:accounts`
   после этого ничего не заводит — так и должно быть.
5. **Перенести снимки и записи**: `uchetkin-dev-acts → uchetkin-prod-acts`,
   `uchetkin-dev-calls → uchetkin-prod-calls` — `aws s3 sync` (в контейнере с
   машины) со статическим ключом, у которого чтение dev-бакетов и запись
   prod-бакетов; ключ выпустить на время переезда и отозвать сразу после.
   Подписанные ссылки в базе не хранятся — считаются при показе, поэтому
   смена бакета им не мешает.
6. **Переключить**: на старой машине заменить `Caddyfile` на перенаправление
   `:80 { redir https://<имя prod>{uri} permanent }` и `docker compose up -d
   caddy` — закладки сотрудников приведут на новый адрес. Обновить адрес в
   инструкциях (`docs/train`, одна константа) и в `docs/launch.md`.
7. **Заполнить внешние секреты** prod в консоли: Новофон (и адрес вебхука в
   кабинете), «Аршин», Карты (ограничение ключа по новому имени), SMTP, каналы
   сторожа. Пока пусто — те же ограничения, что на пилоте.
8. **Вернуть dev роль dev** через несколько дней, когда переезд подтверждён:
   очистить базу (`purge-demo.sql` не подходит — это уже живые данные; `npm run
   seed` с осознанием, что старое стирается), снять перенаправление, вернуть
   расписание `uat.yml`.

Откат в течение этих дней — снять перенаправление на старой машине и
`docker compose up -d api`: данные, введённые в prod за это время, придётся
перенести обратно дампом, поэтому тянуть с решением не стоит.

### Что нельзя делать на prod руками

- **Собирать и запускать образы на машине** (`git pull`, `docker build`,
  `:manual`): в prod попадает только то, что собрано «Выкладкой в prod» из
  тега, — иначе `releases.log` врёт, откат по тегу невозможен, а
  `/opt/uchetkin/src` там и не нужен.
- **Править `/etc/uchetkin/app.env`, `Caddyfile`, `compose.yml` на месте**: их
  пишут cloud-init и выкладка, следующий apply или релиз перетрёт правку. Нужно
  изменить — переменная в `prod.tfvars` или файл в `deploy/`, затем apply или
  выкладка.
- **Запускать `npm run seed`, `uat-stand`, `purge-demo.sql`, `migrate:down`** —
  они стирают данные. Миграции идут только внутри `deploy.sh`.
- **Менять в консоли то, что ведёт Terraform** (группы безопасности, ВМ,
  кластер, бакеты, роли): следующий `plan` это откатит, и хорошо если до, а не
  после того, как кто-то на это положился. Исключение — значения внешних
  секретов в Lockbox: они и должны вноситься в консоли.
- **Открывать SSH «на минутку»**: белый список `ssh_allowed_cidrs` пуст
  намеренно; вход — серийная консоль или OS Login, и то и другое проходит через
  учётные записи облака и остаётся в Audit Trails.
- **Автотесты и нагрузочные прогоны** (`uat.yml`, `e2e/`) — только на dev.

## Переезд на боевой домен (пункт `cloud-domain`)

Решение владельца: живой домен подключается в самом конце, после запуска. Адрес
системы живёт в одной переменной `app_domain` (`infra/README.md`, «Где живёт
доменное имя»), поэтому сам переезд — это `apply`, несколько файлов на машине и
несколько кабинетов. Что для этого описано в Terraform — `infra/README.md`,
«Что меняется при переезде на боевой домен».

**Состояние на 20.09.2026, вечер.** Домен `uchetkin.ru` куплен владельцем
20.09.2026 у Reg.ru (регистратор `REGRU-RU`, оплачен до 20.09.2027). Шаги А, Б
и Г выполнены в тот же день: зона в Cloud DNS, NS у регистратора переключены
на `ns1/ns2.yandexcloud.net` (в реестре `.ru` — с 13:30 UTC, подтверждение
смены по SMS владельца), система переведена на `https://uchetkin.ru`
(Terraform apply — сторож, CORS бакета, метаданные машины; файлы на машине —
руками по таблице шага Г; Caddy получил сертификаты на домен и `www` за
секунды; редиректы со старых адресов проверены; прогон `uat.yml` — таблица в
`docs/uat.md`). Не сделано и ждёт кабинетов: шаг В (домен в Яндекс 360 —
заказчица) и перенастройка Новофона и Карт (ключей ещё нет). Шаг «Через 30
дней» — не раньше 20.10.2026.

### Шаг А — зона в Cloud DNS (сделано 20.09.2026)

В `infra/dev.tfvars`: `manage_dns_zone = true`, `dns_zone_domain = "uchetkin.ru"`,
`dns_ttl = 60`, `mail_records_enabled = true`; `app_domain` при этом **не**
меняется. `apply` создаёт зону и записи: `uchetkin.ru` и `www.uchetkin.ru` — на
адрес машины, MX `mx.yandex.net`, SPF, DMARC. Пока `app_domain` вне зоны,
A-запись кладётся на вершину зоны (`infra/locals.tf`, `app_in_zone`) — так домен
указывает на машину ещё до переключения, и Let's Encrypt сможет его проверить.

Проверка (с узла «Alchemist LAB» — из песочницы порт 53 наружу закрыт):

```bash
dig +short A   uchetkin.ru @ns1.yandexcloud.net   # 84.201.139.101
dig +short MX  uchetkin.ru @ns1.yandexcloud.net   # 10 mx.yandex.net.
dig +short TXT uchetkin.ru @ns1.yandexcloud.net   # "v=spf1 redirect=_spf.yandex.net"
```

### Шаг Б — делегирование (сделано 20.09.2026)

В кабинете Reg.ru у домена заменить DNS-серверы на `ns1.yandexcloud.net` и
`ns2.yandexcloud.net` (карточка домена → «DNS-серверы и управление зоной» →
«сделать это самостоятельно» → «Изменить» → «Свой список DNS-серверов»;
Reg.ru подтверждает смену кодом из SMS владельцу). Это единственное действие
переезда, которое нельзя сделать ни из репозитория, ни из облака: кабинет
регистратора — у владельца домена. 20.09.2026 реестр `.ru` принял смену через
час (12:27 → 13:30 UTC). Проверять надо у серверов зоны `.ru`, а не у своего
резолвера: тот кэширует старые NS на сутки (`dig NS uchetkin.ru
@a.dns.ripn.net +noall +authority`). Готовность:

```bash
dig +short NS uchetkin.ru            # ns1.yandexcloud.net. ns2.yandexcloud.net.
dig +short A  uchetkin.ru            # 84.201.139.101, уже без указания сервера
```

### Шаг В — почтовый домен (нужен кабинет Яндекс 360)

В Яндекс 360 для бизнеса (`admin.yandex.ru`) добавить `uchetkin.ru`; строку
подтверждения `yandex-verification: …` вписать в `mail_verification_txt`, после
подтверждения значение DKIM из «Почта → DKIM» — в `mail_dkim_public_key`, и
`apply`. Завести ящик отправителя (например `uvedomleniya@uchetkin.ru`) и в его
настройках — пароль приложения: обычный пароль SMTP Яндекса не принимает.
Подробности и проверка доставки — `docs/notify.md`, «Свой почтовый домен».

### Шаг Г — день переезда (30 минут, вечером; сделано 20.09.2026, 18:31–18:45 по Екатеринбургу)

1. **Копия.** Запустить службу `uchetkin-backup` и дождаться строки «→ s3://…»
   в её журнале (раздел «Резервные копии»).
2. **Переключить Terraform.** В `dev.tfvars`: `app_domain = "uchetkin.ru"`,
   `legacy_redirect_from = ["http://84.201.139.101", "84-201-139-101.sslip.io",
   "www.uchetkin.ru"]` — старый адрес, старое имя и www ведут на домен. `apply`.
   A-запись переедет с вершины зоны на сам домен без изменения значения.
3. **Разложить файлы на машине.** На **принятой** в состояние ВМ cloud-init
   повторно не запускается (`infra/README.md`, «Машина принята, а не создана»),
   поэтому то, что он написал бы, кладётся руками по выходам `terraform output`:

   | Файл | Что в нём меняется |
   | --- | --- |
   | `/opt/uchetkin/app.env` | `PUBLIC_BASE_URL`, `API_BASE_URL`, `WEBHOOK_BASE_URL`, `COOKIE_DOMAIN` — его читает контейнер API (`compose.yml`, `env_file`) |
   | `/etc/uchetkin/app.env` | то же самое: это версия cloud-init, она не должна расходиться с рабочей |
   | `/etc/uchetkin/caddy.env` | `SITE_ADDRESS=uchetkin.ru` |
   | `/opt/uchetkin/config/frontend.json` | `apiBaseUrl`, `publicBaseUrl` — их читает фронт, пересборка не нужна |
   | `/etc/uchetkin/caddy.d/legacy.caddy` | блок редиректа со старых адресов — как в cloud-init |

   Затем `docker compose up -d`; если менялись `Caddyfile` или `compose.yml` —

## Машина и шлюз агента

Пункт плана `cloud-connect`. Фоновые задачи по серверу — чтение и правка
файлов, команды, журналы, миграции на живой базе — ведутся прямо на машине
контура через шлюз агента, а не в локальной песочнице. Браузер остаётся для
того, что делается в веб-кабинетах: консоль облака, кабинет Новофона,
регистратор домена, проверка интерфейса глазами. В панели владельца машина
dev — строка «CRM Учеткин», для агента это узел `crm-uchetkin-prod`.

### Как подключено

| Что | Где | Примечание |
| --- | --- | --- |
| Служба | `agw-node.service` (systemd, включена в автозагрузку, `Restart=always`), пользователь `alchemisttabia` | поставлена руками 18.09.2026, в cloud-init не входит |
| Файлы агента | `/home/alchemisttabia/.agw-node/`: `agent.sh` — сам агент, `env` — адрес шлюза, одноразовый токен установки и отпечаток ключа шлюза, `token` — постоянный токен машины (0600) | ничего другого постоянного на машине нет |
| Направление связи | только исходящее: агент сам опрашивает `https://agent.alchemist-lab.ru:8787` и забирает задания, входящих портов не нужно | шлюз проверяется по закреплённому публичному ключу (`--pinnedpubkey`), а не по имени в сертификате |
| Что умеет | выполнить команду, прочитать файл, записать файл — от имени `alchemisttabia`, у которого `sudo` без пароля | значит, каждый, кто ставит задания этой машине в панели, — root на ней |
| Рабочий каталог | `/opt/uchetkin/src` — клон `github.com/Alchemist8931/CRM_Poverka`, только чтение: учётных данных GitHub на машине нет, адрес для `push` выключен (`git remote -v` показывает `no_push`) | из него собираются образы `:manual` (`docs/uat.md`), поэтому `git pull` здесь — шаг выкладки, а не рутина; `git fetch` безопасен |
| Журнал агента | `sudo journalctl -u agw-node -n 50` | «машина зарегистрирована» — обмен токена прошёл; `curl: (56)` — шлюз был недоступен, агент повторяет через 5 с |

Установка целиком (точную строку с токеном даёт панель в строке машины):

```sh
mkdir -p ~/.agw-node && chmod 700 ~/.agw-node
curl -sS -k --pinnedpubkey 'sha256//<отпечаток ключа шлюза>' \
  -o ~/.agw-node/agent.sh https://agent.alchemist-lab.ru:8787/node-agent.sh
# /etc/systemd/system/agw-node.service: User=alchemisttabia,
#   EnvironmentFile=/home/alchemisttabia/.agw-node/env,
#   ExecStart=/bin/sh /home/alchemisttabia/.agw-node/agent.sh, Restart=always
umask 077; printf 'AGW_URL=…\nAGW_TOKEN=…\nAGW_PIN=…\n' > ~/.agw-node/env
sudo systemctl enable --now agw-node
```

Токен установки одноразовый и живёт 15 минут: при первом запуске агент меняет
его на постоянный и кладёт в `token`. После этого `AGW_TOKEN` в `env` и в
истории оболочки — пустышка, по ней ничего сделать нельзя. Если 15 минут
прошли до запуска, панель выдаёт новый токен в той же строке машины.

### После перезапуска машины

Служба включена в автозагрузку: после `reboot` агент поднимается сам с тем же
постоянным токеном, и через несколько секунд машина снова «на связи». Делать
ничего не нужно.

Панель показывает «ждёт установки» в двух случаях:

- машину пересоздал Terraform (вариант В выше): диск новый, `~/.agw-node/`
  нет, агент в cloud-init не входит;
- строку машины в панели удалили и завели заново: старый постоянный токен
  шлюз больше не принимает, в журнале агента — отказы шлюза.

Порядок в обоих случаях: в панели в строке машины взять команду установки
(истёк — обновить там же); на машине через серийную консоль или SSH
выполнить `sudo systemctl stop agw-node; rm -f ~/.agw-node/token` — иначе
агент увидит старый файл и регистрироваться не станет; выполнить команду
установки; убедиться: `systemctl is-active agw-node` — `active`,
`sudo journalctl -u agw-node -n 5` — «машина зарегистрирована».

### Отозвать доступ

1. В панели удалить строку машины: постоянный токен перестаёт действовать
   сразу, агент получает отказ и ничего не выполняет.
2. На машине снять службу и файлы:

   ```sh
   sudo systemctl disable --now agw-node
   sudo rm /etc/systemd/system/agw-node.service && sudo systemctl daemon-reload
   rm -rf ~/.agw-node
   ```

Остановить на время, не отзывая: `sudo systemctl stop agw-node`, обратно —
`start`. Пока служба стоит, машина в панели «не на связи»: агент задания не
забирает, и они возвращаются с отказом.

### Разграничение dev и prod

Агент на dev-машине к prod доступа не имеет потому, что prod — другая ВМ с
другим сервисным аккаунтом в другом каталоге облака, а не потому, что на
dev-машине что-то ограничено: `sudo` у агента без пароля. Поэтому машину
prod подключать **отдельной строкой в панели и только с ведома владельца**
(пункт `cloud-prod`); одну строку на два контура не заводить.

Проверено 18.09.2026 на dev:

- ключей облака на машине нет: ни профилей `yc`, ни файлов ключей сервисных
  аккаунтов; `/root/.docker/config.json` без учётных данных (`"auths": {}`).
  IAM-токен приложение и вход в Container Registry берут из метаданных ВМ по
  её сервисному аккаунту (`server/src/secrets.ts`, `infra/README.md`);
- `/etc/uchetkin/app.env` и `/opt/uchetkin/app.env` — только конфигурация и
  идентификаторы секретов Lockbox; в окружении контейнера `uchetkin-api` нет

  старте;
- единственный пароль в файле — `/opt/uchetkin/db.env` (root, 0600): пароль

- поиск по `/opt/uchetkin` без `node_modules` и по истории оболочки на образцы

  единственное попадание в истории — команда установки агента с уже
  использованным одноразовым токеном;
- права сервисного аккаунта ВМ выданы на каталог своего контура
