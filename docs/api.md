# API CRM «Учёткин»

Пункт плана **be-api**. Документ объясняет устройство: что где лежит, как устроен
вход и какие бизнес-правила переехали из прототипа. Машинное описание всех адресов
отдаёт сам сервер по `GET /docs` в формате OpenAPI 3 — там же тела запросов и
параметры, и оно не может разойтись с кодом, потому что собирается из него.

## Как поднять

```bash
docker compose up -d          # из корня репозитория: PostgreSQL 16, API и фронт
curl -s localhost:3000/health # {"status":"ok","db":"ok","version":"1.0.0"}
curl -s localhost:3000/docs   # описание OpenAPI
```

Без Docker, но и без PostgreSQL на машине — API на встроенной базе (PostgreSQL,
собранный в WebAssembly): миграции, демо-набор и сервер поднимаются одной
командой за полминуты. Этим стендом проверяется фронт (пункт **be-fe-wire**):

```bash
cd server && npx tsx scripts/dev-pglite.mts 3000
```

Без Docker — то же самое руками:

```bash
cp env.example .env && npm install
npm run migrate:up && npm run seed
npm start                     # tsx src/api/server.ts
```

Демо-учётки после `npm run seed`: логин совпадает с идентификатором сотрудника
(`sv` — руководитель, `o0` и `o1` — старшие операторы, `o2` и `o3` — операторы,
`v0`…`v11` — поверители), пароль у всех `1234` (меняется переменной `SEED_PASSWORD`). Это набор
для разработки и тестового контура; выдача и смена настоящих паролей — пункт
**be-users**.

## Переменные окружения

| Переменная | Зачем |
|---|---|
| `DATABASE_URL` | соединение с PostgreSQL |
| `PORT`, `HOST` | где слушать (по умолчанию 3000 и 0.0.0.0) |
| `SESSION_SECRET` | ключ подписи сессионных cookie; в рабочем контуре обязателен, короче 16 знаков не принимается |
| `NOVOFON_WEBHOOK_SECRET` | ключ подписи вебхуков телефонии; без него приёмник отвечает 503 |
| `SEED_PASSWORD` | пароль демо-учёток при наполнении |

## Вход и роли

Вход — `POST /api/auth/login` с логином и паролем. В ответ уходит cookie
`uchetkin_session` (httpOnly, SameSite=Lax, Secure в рабочем контуре) на 12 часов.
Внутри cookie только идентификатор сотрудника, срок и подпись HMAC — состояния на
сервере сессия не держит и поэтому переживает перезапуск и второй экземпляр за
балансировщиком.

Роль и блокировка читаются из карточки сотрудника на **каждый** запрос, а не берутся
из cookie: заблокированная учётка перестаёт работать сразу. Цена решения — выход с
одного устройства не гасит сессии на других; список сессий и второй фактор — **cloud-sec**.

Четыре роли те же, что в прототипе: `operator`, `senior`, `supervisor`, `verifier`.

| Правило доступа | Где проверяется |
|---|---|
| поверитель видит только свои маршруты, точки и чат | `canSeeRoute` |
| поверитель заполняет акт только по своим адресам | `actorOr403` в `routes/act.ts` |
| свой заработок и подотчёт видит каждый, чужой — руководитель | `canSeeEarningsOf` |
| прайс и сдельные ставки меняет руководитель | `canEditPrices` |
| день, сборка маршрутов и компетенции — руководитель | `requireRole(..., 'supervisor')` |
| лента звонков — операторам и руководителю, не поверителю | `routes/calls.ts` |

Отказ правила — это `422` с человеческим текстом в поле `error` и коротким
`reason` (`lock`, `cap`, `role`, `act`, …). Тексты те же, что показывал прототип
всплывающей подсказкой: оператор читает их клиенту вслух, менять формулировки нельзя.
`401` — нет сессии, `403` — не та роль там, где дело не в правиле, а в доступе,
`400` — запрос не прошёл схему, `404` — нет такой записи.

      audit.ts          журнал действий: чтение и выгрузка, только руководителю
  storage.ts            Object Storage: ключи, подписанные ссылки, миниатюры
scripts/
  audit-prune.mts       чистка журнала по сроку хранения (`npm run audit:prune`)

  rules.test.ts         правила без базы

Правила намеренно отделены от обработчиков: обработчик достаёт данные и применяет
решение, решение принимает `rules.ts`. Из-за этого правило проверяется тестом за
миллисекунды и читается целиком, не разбираясь в запросах.

## Бизнес-правила, переехавшие из прототипа

| Правило | Было в `index.html` | Стало |
|---|---|---|
| замок даты | `dayLock`, `lockedFor` | `dayLock(facts)`, `lockedFor(facts, role)`; факты — открытый конструктор (`route_builder`) и собранные маршруты |
| загрузка дня и города | `dayTotal`, `dayState` | те же пороги: `off` / `free` / `fill` (≥50 %) / `full` (≥100 %) / `over` (>110 %) |
| потолок приёма | косвенно, через плитку | `cityCapProblem`: оператору отказ, когда с новой заявкой город уходит за +10 %; руководителю — никогда |
| подсказка дат | `slotsFor` | `slotsFor(days, ids, city, limit)`: город в дне, план не выбран целиком, дата без замка, в смене есть поверитель на **все** выбранные услуги |
| цена и скидка | `priceOf`, `priceOfDev`, `discountOf` | те же функции поверх справочника: юрлицу — тариф юрлица, пенсионная скидка стоит на приборе |
| сдельная | `rateV`, `rateO` | `rateV`, `rateO`: от скидки и типа клиента не зависят |
| потолки планирования | `MAX_CITIES`, `MAX_OPS` | те же 5 и 4, плюс проверка состава смены в `dayProblem` |
| обзвон | `callStop` | `POST /api/routes/{id}/stops/{requestId}/call`: отказ отменяет заявку, перенос возвращает её оператору, обзвон целиком переводит маршрут в «обзвонен» |
| закрытие позиции | `closeStop` | `closeProblem`: услуга в каждой строке, заводской номер (кроме причины «нечитаемый номер»), пояснение к «другое», номер бланка |
| необслужено | `markUnserved` | `unservedProblem` + запись в лист ожидания |
| оплата на месте | `payInit`, `setPay` | `PUT /api/requests/{id}/payment`: по счёту — только юрлицу, «не оплачено» — долг с нулевой суммой |
| подотчёт | `subReport` | `GET /api/handovers`: собрано минус сдельная минус сданное |

Цена и ставки записываются в строку прибора **снимком** в момент закрытия позиции
(`price_charged`, `rate_verifier`, `rate_operator`). Переписанный прайс не меняет ни
закрытый акт, ни начисленную по нему сдельную — это проверяется тестом.

### Что добавил фронт

Экраны собираются из срезов, а не из всей базы, и три мелочи в списке заявок
появились именно поэтому (пункт **be-fe-wire**):

| Параметр `GET /api/requests` | Зачем |
|---|---|
| `own=true` | свои заявки: оператору — принятые им, поверителю — выполненные им. Без этого экран заработка тянул бы месяц по всей конторе |
| `with=devices,payment` | приборы и оплата к каждой заявке одним запросом: начисление и цена считаются по строкам приборов, а заявок на экране сотни |

`GET /api/clients` отдаёт историю карточками заявок целиком, а не выжимкой: по
ней оператор подставляет в новое обращение адрес, контакты и тип клиента.

### Фотографии акта

Кадр не идёт через сервер ни в одну сторону: их около ста тысяч в год, и гонять
их через приложение — это платить за трафик дважды. Круг такой:

1. `POST /api/devices/{id}/photos/upload` — сервер проверяет право на акт и
   лимиты и отдаёт подписанную ссылку на `PUT` в бакет (15 минут) и ключ вида
   `acts/год/месяц/заявка/прибор/кадр.jpg`;
2. телефон кладёт снимок прямо в Object Storage по этой ссылке;
3. `POST /api/devices/{id}/photos` — подтверждение. Сервер смотрит, что объект
   действительно лежит и весит не больше пяти мегабайт, делает миниатюру 320 px
   (sharp, префикс `thumbs/`) и записывает ключ, размер, время и размеры кадра.

Показ — в два шага. Ссылка `/api/photos/{id}/file?v=full|thumb&exp=…&sig=…`
сессии не требует (тег `<img>` её и не носит): доступ даёт HMAC от номера кадра,
вида и срока тем же ключом, что подписывает сессию. Дальше сервер отвечает 302 на
подписанную ссылку хранилища с тем же остатком срока. Адрес бакета в базу и в
разметку не попадает, а утёкшая ссылка живёт четверть часа. Подделанная подпись,
просроченный срок и подпись от другого вида кадра — 403.

Лимиты: **5 МБ** на кадр и **10 кадров** на прибор (заказчику на ответ хватает
трёх). Проверяются дважды — по заявленному размеру до загрузки и по факту при
подтверждении, потому что верить можно только объекту в бакете.

Удаление — `DELETE /api/photos/{id}`, только руководителю и только пометкой
(`photos.deleted_at`): кадр уходит из акта, файл в хранилище остаётся (срок
хранения не меньше шести лет, и права удалять у приложения нет — `storage.viewer`
и `storage.uploader`, infra/storage.tf). В журнал действий идёт запись `удаление`
по сущности `photos` с ключом убранного кадра.

Пока хранилище не подключено (машина разработчика без MinIO, тестовый стенд),
загрузка честно отвечает 503, а выдача рисует заглушку с заводским номером
прибора — экран поверителя должен работать целиком, а не наполовину.

### Приёмник вебхуков звонков

Заглушка по существу, но не по поведению. Подпись проверяется по-настоящему:
HMAC-SHA256 по **сырому** телу ключом `NOVOFON_WEBHOOK_SECRET`, заголовок
`X-Signature`. Обработчик заводит строку в `calls`, привязывает звонок к оператору
по внутреннему номеру и к клиенту по телефону — и сразу отвечает 200: АТС не ждёт,
она повторит доставку. Запись разговора докачивает worker, карточку при входящем
поднимает фронт — это пункт **int-novofon**.

### Журнал действий

Пишет журнал не обработчик, а промежуточный слой поверх всех маршрутов сразу
(`src/api/audit.ts`). Причина простая: журнал, который ведут по одному
обработчику, отличается от отсутствующего только тем, что выглядит полным —
забытый вызов не видно ни на экране, ни в тестах соседнего маршрута.

Как он работает:

1. `preHandler` по адресу запроса снимает строку «до» (`/api/requests/{id}` →
   строка `requests`);
2. `onSend` снимает строку «после», считает разницу **по полям** и записывает её.
   Номер созданной записи берётся из ответа: до ответа его не существует.

Что попадает в запись: кто (`actor_id`, роль на момент действия), когда, с какого
адреса и каким браузером, сущность и её идентификатор, `before`/`after` только по
изменившимся полям. Поля с паролями и подписями заменяются на `···` — журнал не
место для секретов. Там, где менялась не сама строка, а её окружение (состав
маршрута, компетенции поверителя, обзвон точки), в `after` идёт тело запроса:
пустая запись хуже приблизительной. У удаления «до» пишется целиком — строки
больше нет, и восстанавливать по разнице полей будет нечего.

Отдельными действиями пишутся `вход`, `выход`, `неудачный вход` (актёр
неизвестен, известен только логин — по ним видно перебор паролей), `просмотр`
карточки клиента, `прослушивание` записи разговора (в том числе отказ: обращение
к записи по 152-ФЗ должно быть видно, чем бы оно ни кончилось) и `выгрузка`
журнала. Вебхук телефонии в журнал не идёт: это не человек, а АТС.

Читает журнал только руководитель: `GET /api/audit` с отбором по сотруднику,
сущности, действию и датам и поиском по номеру заявки (он ищется и в `entity_id`,
и внутри снимков), `GET /api/audit/export.csv` — тот же отбор файлом для Excel
(разделитель `;`, метка порядка байтов). Выгрузка сама попадает в журнал.

Срок хранения — три года. Записи не правятся и не удаляются: `UPDATE` запрещён
всегда, `DELETE` — пока записи нет трёх лет, и держится это триггером в базе
(`migrations/1757980600000_audit`), а не дисциплиной обработчиков. Просроченное
убирает `npm run audit:prune` (в контуре — по расписанию, пункт **cloud-ops**).

### Платежи

Провайдера эквайринга нет, и `GET /api/payments/{id}/status` честно отвечает
`provider: null`, выводя состояние из способа и отметки о приёме денег: `долг`,
`ожидает приёма`, `принят`. Место под настоящий статус оставлено там же — пункт
**int-pay**.

## Проверки

```bash
npm test          # правила и API целиком, без Docker и без сети
npm run typecheck # типы
npm run check     # схема, документ, наполнение (пункт be-schema)
```

Экран журнала против настоящего API проверяется из фронта:
`cd web && npm run build && npm run check:audit-ui` — строки, отбор, поиск,
раскрытие в разницу по полям, выгрузка и то, что оператору журнала не видно.

`npm test` поднимает настоящий PostgreSQL, собранный в WebAssembly, применяет
миграции и гоняет весь API через `app.inject()`. Две грабли, обе выяснены опытом:
миграции применяются чтением Up-части файлов (node-pg-migrate нужен сетевой адрес,
а сетевой слой PGlite ломается на длинных пачечных вставках), и стенд поднимается
заново на каждую проверку — тесты меняют данные и не должны зависеть от порядка.

## Чего здесь нет

Записи разговоров в хранилище ещё не появляются: `GET /api/calls/{id}/record`
отдаёт подписанную ссылку, когда запись докачана, а докачивает её worker — пункт
**int-novofon**. Само обращение к записи журнал пишет уже сейчас. Импорт справочников и клиентской базы заказчика сделан отдельным
инструментом командной строки, мимо API — **be-import**, [`import.md`](import.md). Уведомления
клиентам — **int-notify**. Записи о поверке в «Аршин» — **int-arshin**.
