# Схема базы CRM «Учёткин»

Пункт плана **be-schema**. Документ описывает таблицы, связи и принятые решения.
Исходники: миграции в `server/migrations/`, наполнение демо-данными в `server/src/seed/`.

Схема повторяет модель прототипа (`index.html`, объект `S`) и добавляет к ней то,
чего в памяти браузера быть не могло: учётные данные сотрудников, деньги, взятые
поверителем на руки, журнал звонков и журнал действий. Основание — «Учёткин —
архитектурное решение», разделы 5–7.

## Как поднять

```bash
cd server
docker compose up -d          # PostgreSQL 16 на localhost:5432
cp env.example .env           # DATABASE_URL уже указывает на неё
npm install
npm run migrate:up            # применить миграции
npm run seed                  # наполнить демо-данными прототипа
```

`npm run migrate:down` откатывает последнюю миграцию, `npm run db:reset` — полный
круг «снести всё → применить → наполнить». `npm run check` прогоняет проверку
целиком на временной базе, не трогая ничего на машине (см. «Проверка» в конце).

## Из чего состоит

Девятнадцать таблиц в трёх миграциях. Разбиение не косметическое: справочники
меняются руками руководителя, рабочие данные пишут все четыре роли, а связь и
журнал наполняются внешними системами и общим обработчиком API — у этих групп
разный срок жизни и разный порядок отката.

| Миграция | Таблицы |
|---|---|
| `1757980000000_reference` | `cities`, `services`, `device_types`, `staff`, `staff_skills` |
| `1757980100000_operations` | `days`, `absences`, `clients`, `routes`, `requests`, `stops`, `wait_list`, `devices`, `photos`, `payments`, `handovers` |
| `1757980200000_comms_and_audit` | `calls`, `route_chat`, `audit_log` |

## Связи

```

        └──< wait_list.city

services ─┬──< staff_skills.service_id      (компетенции поверителя)

          └──> services.replacement_service (чем менять непригодный прибор)

       ├──< absences.staff_id
       ├──< routes.verifier_id, routes.duty_operator_id
       ├──< requests.operator_id, requests.verifier_id
       ├──< payments.by_staff, handovers.staff_id
       ├──< calls.operator_id, route_chat.author_id
       └──< audit_log.actor_id

clients ──< requests.client_id            (ключ клиента — нормализованный телефон)
        └─< calls.client_id

routes ─┬──< stops.route_id
        ├──< requests.route_id
        ├──< route_chat.route_id
        └──< wait_list.route_id

requests ─┬──< stops.request_id
          ├──< devices.request_id ──< photos.device_id
          ├──< payments.request_id       (одна строка на заявку)
          ├──< wait_list.request_id
          └──< calls.request_id

wait_list ──< devices.replacement_wait_id (отложенная замена ждёт звонка оператора)
```

## Таблицы

### `cities` — города приёма
Ключ — название города: им оперирует и прототип, и планирование дня, где города
лежат массивом в записи дня. Числового идентификатора в этих массивах не будет,
поэтому уникальность названия здесь несущая, а не декоративная.

`weekdays` и `norm_per_verifier` — столбцы листа «Города» справочника, который
заполняет заказчик (дни выезда и норматив адресов на поверителя). Планирование
подставляет их как заготовку, руководитель правит руками.

### `services` — услуги, цены и ставки
Три цены на услугу: физлицо, пенсионер, юрлицо. Скидка пенсионеру — за счёт
компании, сдельные ставки поверителя и оператора от неё не зависят.

`is_verification` отделяет поверку от замены, монтажа и демонтажа: результат
«годен / не годен» бывает только у поверки. `replacement_service` — чем меняют
непригодный прибор: воду заменой счётчика, тепло монтажом теплосчётчика.

### `device_types` — типы приборов
Номер в Госреестре (`grsi`) и межповерочный интервал в годах — в этих единицах он
стоит в паспорте прибора и в справочнике заказчика. Интервал нужен, чтобы посчитать
дату следующей поверки в акте и в записи ФГИС «Аршин».

### `staff` — сотрудники и их доступ
Идентификатор текстовый и осмысленный (`v0`, `o1`, `sv`) — тот же, что в прототипе:
перенос данных и разбор демо-набора должны читаться глазами.

Учётные данные лежат здесь же, а не в отдельной таблице: по архитектурному решению
человек и доступ заводятся одной карточкой. Логика выдачи, сброса и второго фактора —
пункт **be-users**, здесь только поля (`login`, `password_hash`,
`must_change_password`, `otp_hash`, `otp_expires_at`, `mfa_secret`, `blocked_at`).
Учётка не удаляется, а блокируется: человек остаётся во всей истории, но войти
не может. Логин нечувствителен к регистру — уникальный индекс стоит по `lower(login)`.

### `staff_skills` — компетенции поверителя
Кто какие услуги закрывает. Распределены неровно: воду умеют почти все, тепло —
трое, демонтаж один. Из-за этого часть услуг в отдельные даты недоступна, и подбор
поверителя на заявку обязан это учитывать.

### `days` — план дня
День планирует руководитель целиком: города приёма, план по каждому городу, смена
поверителей, смена операторов. Всё остальное считается от этой записи, поэтому
ключ — сама дата.

Города и смены лежат массивами, план — объектом `{"Екатеринбург": 25}`. Это форма
прототипа, и она здесь уместна: запись дня всегда читается и пишется целиком,
отдельной строки состава смены никто не запрашивает. Цена решения — на массивы не
повесить внешний ключ, целостность состава смены проверяет сервер при записи дня.

Внешнего ключа от `requests.date` к `days.date` нет намеренно: заявку можно принять
на дату, которую руководитель ещё не планировал.

### `absences` — отсутствия
До согласования дни остаются рабочими по графику, поэтому статус лежит в самой
записи, а не выражается её наличием.

### `clients` — клиенты
Отдельной карточки в прототипе не было: заявки связывал только совпадающий номер
телефона. Здесь номер и стал ключом — в нормализованном виде `+7XXXXXXXXXX`,
потому что на приёме его диктуют то через восьмёрку, то со скобками, то без.
Нормализация — `normPhone()` в `server/src/db.ts`, форма проверяется ограничением
`phone_norm ~ '^\+7[0-9]{10}$'`.

### `requests` — заявки
Все поля заявки прототипа: адрес с подъездом, этажом и домофоном, два контакта,
почта, окно приезда (`time_slot` — середина, ±1 час), комментарии отдельно для
оператора и для поверителя, заявленные услуги (`svcs`), статус, оператор приёма,
поверитель, дата приёма звонка.

Адрес и контакты **скопированы** в заявку, а не взяты из клиента ссылкой: поверка
идёт по конкретному адресу в конкретный день, и позднее исправление карточки
клиента не должно менять того, что записано в уже закрытом акте.

Статусы: `создана`, `в маршруте`, `выполнена`, `перенос`, `отменена`, `ожидание`.

### `routes` и `stops` — маршруты и точки
Маршрут — день, город, поверитель и дежурный оператор, который ведёт его по связи.
Статусы: `черновик`, `обзвонен`, `в работе`, `выполнен`.

Точка держит позицию в объезде, результат обзвона (`подтверждена` / `перенос` /
`отказ`), отметку о выполнении и причину, по которой адрес не обслужили. Причина
нужна оператору, чтобы перезвонить клиенту и переставить его на другой день.

Ограничения, за которыми стоит правило работы, а не аккуратность:
- `stops_done_xor_unserved` — выполненная точка не может быть необслуженной;
- `stops_other_needs_note` — причина «Другое» без пояснения бесполезна: звонить клиенту не с чем;
- `stops_route_position_key` отложенный (`DEFERRABLE`), иначе перестановку точек
  местами пришлось бы делать через временные значения позиций.

### `wait_list` — лист ожидания
Адрес, который не закрыли, и замена, которую клиент отложил. `kind` различает эти
два случая (`адрес` / `замена`), `state` ведёт запись от `не обработана` через
`перенесена` или `снята` к `отменена`, `moved_to` указывает на новую заявку.

Таблица заведена **сверх перечня задачи**: без неё демо-набор прототипа — экран
необслуженных адресов (**fe-unserviced**) и отложенные замены (**fe-negative**) —
в базу не ложится.

### `devices` — приборы в акте
Услуга стоит в строке прибора, а не в заявке: на одном адресе один счётчик
поверяют, второй меняют, и цены у них разные.

Результат поверки — `bad` с причиной из четырёх (`Погрешность выше допуска`,
`Механическое повреждение`, `Нечитаемый номер`, `Другое`). Свидетельство о
непригодности выписывается от руки на бумажном бланке, в базе от него остаётся
только номер (`blank_no`, нумерация сквозная у заказчика). Заводского номера может
не быть вовсе — ровно в случае «нечитаемый номер».

`price_charged`, `rate_verifier`, `rate_operator` — **снимок** цены и ставок на
момент выполнения. Переписанный прайс не должен менять ни закрытый акт, ни уже
начисленную по нему сдельную оплату. Это прямое требование архитектурного решения.

### `photos` — фото выполненных работ
Сам файл лежит в Object Storage и через сервер не идёт: телефон получает подписанную
ссылку и льёт снимок напрямую. В базе только ключ по раскладке архитектурного
решения — `acts/{год}/{заявка}/{прибор}/{uuid}.jpg`, имя файла с телефона, время
съёмки, размер и контрольная сумма. `thumb_key` заполняет worker, сделав миниатюру.

### `payments` — оплата на месте
Эквайринга на первом этапе нет: поверитель берёт наличные или перевод на карту и
держит деньги у себя как подотчёт до конца месяца. По счёту платит только юрлицо —
эти деньги через руки поверителя не проходят.

`amount` — сколько взяли на самом деле, `charged` — сколько стоило по прайсу:
клиент округляет, не добирает пару сотен, обещает довезти. `не оплачено` — это долг,
а не платёж на ноль рублей, поэтому сумма при нём обязана быть нулевой.

### `handovers` — сдача подотчёта
Поверитель привозит руководителю собранное за месяц за вычетом своей сдельной
оплаты. Сдача привязана к месяцу, за который её принесли, а не ко дню приёмки:
деньги за август обычно везут в первых числах сентября.

Заведена **сверх перечня задачи** по той же причине, что и лист ожидания: иначе
экран подотчёта (**fe-payment**) не из чего собрать.

### `calls` — звонки
Строку заводит вебхук Новофона: приложение кладёт задание в очередь и отвечает 200,
запись разговора докачивает worker — АТС нас не ждёт. Поэтому `record_key`
заполняется позже самой строки и допускает NULL.

### `route_chat` — переписка по маршруту
Оператор и поверитель: «не открывают», «снимать счётчик?». Привязана к маршруту,
а не к адресу: разговор идёт про выезд целиком.

### `audit_log` — журнал действий
Нужен и руководителю (кто переставил заявку), и 152-ФЗ: каждое прослушивание записи
разговора и каждый просмотр карточки клиента — это обращение к персональным данным.
Состояние «до» и «после» пишется объектом `jsonb`: набор полей у сущностей разный,
а журнал должен пережить изменение схемы, не ломаясь и не требуя миграции.

## Индексы

Требуемые пунктом плана:

| Индекс | Зачем |
|---|---|
| `requests_date_city_idx` на `requests (date, city)` | основной разрез приёма и планирования |
| `requests_phone_idx` на `requests (phone_norm)` | история клиента и проверка дублей |
| `stops_route_idx` на `stops (route_id)` | маршрут читается целиком |
| `calls_started_idx` на `calls (started)` | лента звонков и отчёты по нагрузке на линию |

Остальные закрывают частые выборки экранов: `routes (date, city)`,
`routes (verifier_id, date)`, `requests (status, date)`, `requests (verifier_id, date)`,
`devices (request_id)`, частичный `devices (request_id) WHERE bad`,
`photos (device_id)`, частичный `payments (by_staff, paid_at)` по деньгам на руках,
`handovers (staff_id, period)`, `wait_list (city, at) WHERE state = 'не обработана'`,
`route_chat (route_id, at)` и три по `audit_log`.

## Время и деньги

Время везде `timestamptz`. Прототип пишет время строками без зоны
(`2026-09-15 14:30`), и при переносе зона названа явно — Екатеринбург, UTC+5
(`TZ_OFFSET` в `server/src/db.ts`). Без этого акты и платежи разъехались бы на пять часов.

Деньги — целые рубли (`integer`). Копеек в прайсе нет, дробных начислений тоже:
цены и ставки заданы круглыми суммами, клиент платит наличными.

## Наполнение демо-данными

`server/src/seed/prototype-model.mjs` — **дословные куски** `index.html`, а не
пересказ: тот же генератор с тем же зерном, тот же порядок обращений к нему, те же
доли и округления. Любая перестановка строк меняет поток случайных чисел, а с ним
и весь набор. Файл не правится руками: поменялась модель в прототипе — блоки
переносятся заново целиком.

`server/src/seed/load.ts` раскладывает готовое состояние по таблицам. Решений о
том, сколько чего сгенерировать, в нём нет и быть не должно.

## Допущения, которые нужно подтвердить заказчиком

1. **Межповерочный интервал.** Прототип его не хранит — там его негде было
   показать. Проставлен по описаниям типов в Госреестре: холодная вода 6 лет,
   горячая 4, теплосчётчик 4 (`DEVICE_TYPE_EXTRA` в `server/src/seed/load.ts`).
   Заказчик подтверждает листом «Приборы» справочника, пункт **be-import**.
2. **Дни выезда и норматив адресов.** В прототипе зашиты в расписание
   (пн/ср/пт — Екатеринбург, вт/чт — Нижний Тагил, сб — Каменск-Уральский,
   25 адресов на поверителя в смене). Перенесены в `cities` как заготовка;
   лист «Города» справочника их уточнит.
3. **Время приёма заявки.** Прототип запоминает только день звонка, не час.
   `created_at` выставлен на начало дня приёма.

## Проверка

`npm run check` в каталоге `server` — два шага, оба с кодом возврата:

1. **`check:model`** — каждый перенесённый в `prototype-model.mjs` блок обязан
   лежать в `index.html` дословно; плюс отпечаток набора (числа по сущностям,
   сумма платежей, первая и последняя заявка), который сверяется с прототипом,
   открытым в браузере.
2. **`check:schema`** — на пустой базе: применить миграции → откатить последнюю →
   применить снова → наполнить демо-данными → сверить объём.

Проверка поднимает настоящий PostgreSQL, собранный в WebAssembly (PGlite), во
временном каталоге и ничего не трогает на машине. Это нужно там, где нет Docker;
с `docker compose up -d` те же шаги идут по `DATABASE_URL` из окружения.

Две особенности стенда, обе выяснены опытом и записаны в
`server/scripts/check-schema.ts`: сетевой слой PGlite не собирает сообщение
протокола обратно, если оно пришло несколькими пакетами (поэтому миграции идут
через сокет, а наполнение — прямо в базу), и без каталога на диске PGlite держит
всю базу в куче WebAssembly и не доживает до конца набора.

## Что этот пункт не закрывает

REST API и перенос бизнес-правил — **be-api**. Учётные записи и выдача доступа —
**be-users** (поля в `staff` готовы). Загрузка фотографий в Object Storage и
миниатюры — **be-photos**. Импорт справочников и клиентской базы заказчика —
**be-import**. Вебхуки Новофона — **int-novofon**. Экран журнала — **be-audit**.
