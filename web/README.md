# Фронт CRM «Учёткин»

Пункт плана **be-fe-wire**. Прототип, живший одним файлом `index.html`, разобран
на модули и собирается Vite. Подход прежний и менять его незачем: экран — это
функция, которая возвращает строку HTML, `render()` кладёт её в `#root` целиком.
Никакого фреймворка здесь нет и не предполагается.

Работает в двух режимах из одних и тех же исходников:

| Режим | Откуда данные | Когда |
|---|---|---|
| рабочий | API (`/api`), вход по учётной записи | обычная работа, `docker compose up` |
| демо (`?demo=1`) | наполнение в памяти вкладки | показать экраны без сервера; этим же файлом прототип лежит на GitHub Pages |

## Как поднять

```bash
# всё сразу — база, API и фронт на одном адресе
docker compose up -d --build          # из корня репозитория
open http://localhost:8080            # вход sv / o2 / v0, пароль 1234

# только фронт, API уже где-то поднят
cd web && npm ci
npm run dev                           # http://127.0.0.1:5173, /api проксируется на 3000
npm run build && npm run preview      # то же самое, но на собранных файлах
```

Обращения к API идут относительными путями (`/api`, `/health`), и в разработке
их проксирует сам Vite. Так сделано не для красоты: сессия лежит в cookie с
`SameSite=Lax`, и на чужое происхождение браузер её просто не отправит.

Сборки две, из одного дерева исходников:

```bash
npm run build        # web/dist      — рабочая, ходит в API
npm run build:demo   # web/dist-demo — один файл, наполнение в памяти
npm run build:all    # обе + выкладка демо в корневой index.html репозитория
```

## Что где лежит

```
web/src/
  main.js          точка входа: какой режим, слушатели клавиш, запуск
  globals.js       имена модулей в window (разметка зовёт обработчики по имени)
  state.js         S — состояние вкладки, доступ к записи дня и сотрудникам
  refs.js          справочники: города, услуги, приборы, роли, страницы
  rules.js         расчёты: смены, замок даты, цены, ставки, оплата, подотчёт
  util.js          даты, деньги, экранирование
  net.js           слой «нет связи»: опрос /health и размытие поверх интерфейса
  styles.css       весь CSS прототипа, без правок
  api/
    mode.js        демо или рабочий режим, адрес API
    client.js      единственное место, где фронт ходит в сеть
    map.js         строки базы ↔ объекты экранов (client_type ↔ clientType)
    load.js        какой экран какой срез данных грузит
    actions.js     действия: запрос к серверу и перерисовка по ответу
    boot.js        вход, роль, страницы роли
  ui/
    render.js      render(), переходы по страницам, всплывающие подсказки
    shell.js       рельса, шапка, лента ёмкости, состояния загрузки и ошибки
    controls.js    общие контролы: SEL, DATE, CHK, SEG
    modals.js      модальный слой, phone.js, lightbox.js, icons.js, brand.js
  screens/         по файлу на экран: intake, support, plan, routes, myroute, audit, …
  screens/print.js печатные формы: акт выполненных работ и свидетельство о поверке
  demo/seed.js     наполнение прототипа — тот же генератор с тем же зерном
  demo/audit.js    журнал действий для демо-режима (в прототипе его не было)
```

Зависимость одна — Vite (плюс `vite-plugin-singlefile` для демо-сборки и
playwright-core для проверок). Ни библиотеки состояния, ни роутера, ни сборщика
стилей: экран и так собирается строкой.

## Как это работает

**Действие.** В прототипе действие меняло `S` и звало `render()`. Теперь каждое
действие, меняющее данные, уходит в API, а экран перерисовывается по ответу:
правило сначала проверено на сервере, потом картинка. Отказ правила приходит
кодом 422 с тем же текстом, который прототип показывал подсказкой, — его и
показываем. Демо-режим остался как был: тот же код, но ветка «в памяти».

Два исключения, и оба вынужденные: поля строки прибора и сумма оплаты уходят на
сервер с задержкой в полсекунды и **без** перерисовки по ответу. Перерисовывать
страницу на каждую букву нельзя — каретка уедет из поля.

**Загрузка.** Прототип держал в памяти весь набор и считал по нему что угодно.
С базой так нельзя: заявок тысячи. Поэтому каждый экран говорит, какой срез ему
нужен (`api/load.js`), а считает по-прежнему по `S`. Там, где «сколько всего»
по срезу посчитать нечестно — загрузка дня, замок даты, — число приходит с
сервера вместе с днём.

**Связь.** Слой «нет связи» поднимает и снимает `api/client.js`: запрос, не
доехавший до сервера, — это и есть потеря связи, а любой ответ (пусть даже
отказ правила) означает, что связь есть. Опрос `/health` раз в десять секунд
нужен для случая, когда человек ничего не нажимает.

**Фотографии.** Кадр с телефона жмётся прямо в браузере (canvas, 1600 px по
длинной стороне, JPEG 0.82) и уходит в Object Storage **мимо сервера**: сервер
только выдаёт подписанную ссылку на загрузку, а потом, по подтверждению,
записывает кадр в акт и делает миниатюру (`api/actions.js`, круг описан в
`docs/api.md`). В акте показывается миниатюра, оригинал тянется только когда
кадр открыли на весь экран. Свои лимиты — 5 МБ на кадр и 10 кадров на прибор —
экран проверяет до загрузки, но главный здесь сервер: он проверяет их заново.
Убрать кадр из акта может только руководитель, поверителю кнопка не показывается.

## Проверки

```bash
# все экраны трёх ролей против локального API + сквозной сценарий + слой «нет связи»
npm run preview &                 # фронт на 4173 с проксированием на API
npm run e2e                       # API поднимает и роняет сам сценарий

# кадр в акте против живого хранилища: сжатие, загрузка из браузера, лайтбокс
docker compose up -d minio minio-init   # из корня репозитория
npm run build && npm run check:photo-ui

# журнал действий руководителя против настоящего API
npm run build && npm run check:audit-ui

# печатные формы: акт и свидетельство о поверке в PDF на одной странице А4
npm run build && npm run check:print-ui

# снимки экранов на ширине 1600 и сверка компоновки с прежним прототипом
npm run shots -- http://127.0.0.1:8812/index.html ../docs/screens/after
node scripts/compare-shots.mjs ../docs/screens/before ../docs/screens/after
```

`scripts/e2e.mjs` проходит цепочку «заявка → маршрут → акт → отметка оплаты →
подотчёт», перезагружает страницу и смотрит, что всё на месте, а потом
останавливает сервер и убеждается, что слой «нет связи» поднялся и снялся сам.
Браузер берётся из кэша playwright или из `PLAYWRIGHT_CHROME`.

`scripts/check-photo-ui.mjs` про то, чего с сервера не видно: что в хранилище
уезжает сжатый кадр, а не то, что отдала камера, и что браузеру вообще позволено
класть его в бакет: бакет ему чужой адрес, и без разрешения CORS
(`infra/storage.tf`, `cors_rule`) загрузка не начнётся вовсе. Иначе этого не
поймать на машине разработчика:
MinIO пускает любой источник по умолчанию. Круг со стороны сервера проверяет
`server/scripts/check-photo-roundtrip.mts`.

`scripts/check-audit-ui.mjs` проверяет экран «Журнал действий»: правка прайса и
заявки через API появляются в журнале с разницей по полям, отбор по сущности
сокращает таблицу, поиск находит записи по номеру заявки, строка раскрывается в
диф, выгрузка отдаёт CSV и сама попадает в журнал, а оператору страницы журнала
нет ни в меню, ни по адресу.

`scripts/check-print-ui.mjs` — печатные формы (пункт **fe-forms**,
`screens/print.js`). У закрытой позиции в акте поверителя и в карточке
выполненной заявки появляются «Печать акта» и «Свидетельство» на каждый прибор
с результатом «годен»; форма открывается слоем поверх экрана, на бумагу уходит
только лист (`@media print`), печать — `window.print()`. Проверка сохраняет
каждый лист в PDF и считает страницы: их ровно одна, лист не шире полосы
набора; «действительно до» в свидетельстве сходится с датой поверки плюс
межповерочный интервал типа прибора из справочника сервера
(`device_types.interval_years`, на экране — `DEV_TYPES[].mpi`), включая
поверку 29 февраля; номер записи, принятый «Аршином» (`devices.arshin_number`),
доезжает до свидетельства. Своих бланков заказчик не присылал, форма типовая:
реквизиты исполнителя лежат константой `ORG` в `screens/print.js`.

## Чего здесь нет

Учётных записей и смены пароля — **be-users**. Карточки при входящем звонке —
**int-novofon**. Настоящей карты в конструкторе маршрутов — **int-maps**.
