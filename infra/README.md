# Инфраструктура CRM «Учёткин» в Яндекс Облаке

Описание контура кодом: сеть, ВМ, база, хранилище, секреты, DNS. Один корневой
модуль обслуживает оба контура — dev и prod, — они различаются только файлом
переменных и ключом состояния. Контур пересоздаётся с нуля по этому описанию:
при отсутствии у заказчика своего администратора это и есть страховка.

Состав взят из архитектурного решения (пункт плана `arch`, документ «Учёткин —
архитектурное решение», 14.09.2026). Где описание расходится с ним — сказано прямо
в разделе «Отличия от постановки».

| Файл | Что описывает |
| --- | --- |
| `versions.tf` | версии Terraform и провайдеров, хранение состояния в Object Storage |
| `providers.tf` | провайдер Яндекс Облака; учётные данные — только из окружения |
| `variables.tf` | все переменные с описаниями и проверками |
| `locals.tf` | производные значения, в том числе все адреса системы |
| `network.tf` | сеть, подсеть, группы безопасности, статические внешние адреса |
| `iam.tf` | сервисный аккаунт приложения и его права |
| `storage.tf` | бакеты фото актов и записей разговоров, правила хранения, доступ |
| `lockbox.tf` | секреты и кто имеет право их читать |
| `postgres.tf` | Managed Service for PostgreSQL |
| `kms.tf` | ключ шифрования данных и права на него |
| `audit.tf` | Audit Trails: журнал действий в облаке, бакет журналов, его сервисный аккаунт |
| `sws.tf` | Smart Web Security: WAF и защита от ботов перед балансировщиком |
| `check_cloud_init.py` | проверка отрисованного cloud-init: YAML разбирается, меры на месте |
| `compute.tf` | ВМ, cloud-init, расписание снимков диска |
| `registry.tf` | Container Registry, правила очистки, сервисный аккаунт выкладки (порядок релиза — `docs/release.md`) |
| `alb.tf` | Application Load Balancer и Certificate Manager — выключены, см. ниже |
| `dns.tf` | публичная зона Cloud DNS и A-запись |
| `logging.tf` | группа Cloud Logging: журналы контейнеров с ВМ и журнал сторожа, хранение 30 дней |
| `dashboards/` | отдельный корневой модуль с дашбордами Monitoring: машина, HTTP (Caddy), база (при Managed PostgreSQL), балансировщик (при `alb`). Почему отдельно — раздел «Эксплуатация» ниже |
| `backup.tf` | бакет `ops`: ежедневный и еженедельный `pg_dump` с машины, сроки хранения, состояние сторожа |
| `watchdog.tf`, `watchdog/` | сторож — Cloud Function по таймеру: `/health`, диск, копии, 5xx, сертификат → Telegram и почта (порядок действий — `docs/ops.md`) |
| `outputs.tf` | адреса, идентификаторы секретов, что завести в DNS |
| `cloud-init.yaml.tftpl` | первичная настройка ВМ: Docker, Compose, агент мониторинга (метрики и логи), таймеры резервной копии и служебных метрик |
| `dev.tfvars`, `prod.tfvars` | значения контуров |
| `backend-dev.hcl`, `backend-prod.hcl` | где лежит состояние каждого контура |

## Порядок применения

Всё, что ниже, выполняется из каталога `infra`.

**0. Учётные данные — только в окружении.** В репозитории их нет и быть не должно.

```bash
export YC_TOKEN="$(yc iam create-token)"          # либо YC_SERVICE_ACCOUNT_KEY_FILE=...
export AWS_ACCESS_KEY_ID=...                      # статический ключ SA terraform,
export AWS_SECRET_ACCESS_KEY=...                  # им Terraform пишет своё состояние
export TF_VAR_storage_access_key="$AWS_ACCESS_KEY_ID"
export TF_VAR_storage_secret_key="$AWS_SECRET_ACCESS_KEY"
```

**1. Один раз на облако — сервисный аккаунт Terraform и бакет состояния.**
Бакет, в котором лежит состояние, описывать в самом Terraform нельзя, поэтому он
создаётся руками — это единственное действие вне кода:

```bash
yc iam service-account create --name terraform --folder-id <каталог dev или общий>
yc resource-manager folder add-access-binding <каталог dev>  --role editor --subject serviceAccount:<id SA>
yc resource-manager folder add-access-binding <каталог prod> --role editor --subject serviceAccount:<id SA>
yc iam access-key create --service-account-name terraform    # отсюда AWS_* ключи
yc storage bucket create --name uchetkin-tfstate --default-storage-class standard
yc storage bucket update --name uchetkin-tfstate --versioning enabled
```

Имя бакета глобально на всё Object Storage. Если занято — поменять его в обоих
файлах `backend-*.hcl`.

**2. Заполнить идентификаторы.** В `dev.tfvars` они уже стоят (см. «Что
применено»). В `prod.tfvars` остаётся заглушка `PUT-CLOUD-ID-HERE`: её нужно
заменить значениями из пункта `cloud-account`. С заглушкой `terraform plan`
останавливается на проверке формата — молча применить неправильный каталог
не получится.

Там же стоит заполнить `ssh_allowed_cidrs` и `ssh_public_keys`. Пустые списки —
рабочее состояние: порт 22 снаружи не открыт вовсе, вход остаётся через серийную
консоль в консоли облака.

**3. dev.**

```bash
terraform init -backend-config=backend-dev.hcl
terraform fmt -check
terraform validate
terraform plan  -var-file=dev.tfvars -out=dev.tfplan
terraform apply dev.tfplan
```

**4. prod.** То же самое с другим состоянием; `-reconfigure` переключает бэкенд.
Временное имя контура строится из его статического адреса (`<адрес через
дефисы>.sslip.io`), а адрес появляется только при apply — поэтому сначала
резервируется один адрес, потом применяется всё остальное:

```bash
terraform init -backend-config=backend-prod.hcl -reconfigure
terraform apply -var-file=prod.tfvars -target=yandex_vpc_address.vm
terraform output app_external_ip                       # например 84.201.139.101
# в prod.tfvars: app_domain = "84-201-139-101.sslip.io", tls_enabled = true
terraform plan  -var-file=prod.tfvars -out=prod.tfplan
terraform apply prod.tfplan
```

Пока prod не применён, `app_domain` в `prod.tfvars` — заглушка
`prod-address-pending.sslip.io`: формат проходит, но имя никуда не разрешается,
и контур, применённый без первого шага, по имени не откроется.

С 18.09.2026 рабочий контур — dev-машина (пункт `live-ip`), поэтому apply prod
— это не «пустой контур», а переезд живых данных: порядок — `docs/ops.md`,
«Переезд рабочего контура в prod».

**5. После первого `apply`.**

1. Взять `terraform output app_external_ip` и завести A-запись имени контура на
   этот адрес. Пока имя временное и его зона живёт у стороннего регистратора
   (`manage_dns_zone = false`), это делается один раз руками; подсказка с готовой
   строкой — в выходе `dns_record_to_create`. Адрес статический и переживает
   пересоздание ВМ.
2. Дождаться, пока имя начнёт разрешаться, и только потом поднимать Caddy: он
   запрашивает сертификат Let's Encrypt при первом обращении, а неудачные попытки
   упираются в ограничения удостоверяющего центра.
3. Наполнить секреты внешних сервисов в Lockbox (`novofon`, `arshin`, `smtp`,
   `maps`, `payment`). Terraform создаёт их пустыми намеренно: ключ, введённый в
   консоли, не проходит ни через репозиторий, ни через состояние Terraform.
   Идентификаторы — в выходе `lockbox_secret_ids`.
4. Выкладка приложения — пункт плана `cloud-cicd`. Terraform кладёт на ВМ только
   платформенную часть: Docker, Compose, агент мониторинга и файлы конфигурации
   в `/etc/uchetkin`.

### Машина принята, а не создана

В облаке уже стояла ВМ `crm-uchetkin-prod` (`epd7bm5p02135bp5js8i`, создана
руками 09.09.2026). Вместо второй машины она вместе с сетью и подсетью принята

| Значение | Почему именно такое |
| --- | --- |
| `zone = "ru-central1-b"` | зона машины; смена зоны — пересоздание ВМ |
| `vm_name = "crm-uchetkin-prod"` | имя хоста машины; тоже поле пересоздания |

| `vm_core_fraction = 100` | доля vCPU у машины; снижение до 20 % требует её остановки, а экономит ≈ 130 ₽/мес |
| `vm_disk_size = 30` | её диск; уменьшение размера — пересоздание |
| `vm_user = "alchemisttabia"` | пользователь, который на машине уже есть |
| `enable_oslogin = true` | машина создана с OS Login |
| `subnet_cidr = "10.129.0.0/24"` | подсеть зоны b сети `default` |

Принятая сеть и подсеть переименованы в `uchetkin-dev-net` и
`uchetkin-dev-subnet-ru-central1-b`: имя — правка на месте, не пересоздание.
Остальные автоматические подсети (зоны `a`, `d`, `e`) Terraform не ведёт.

Ключ `cloudbackup` в метаданных ВМ исключён из сравнения
(`ignore_changes`): его пишет служба Cloud Backup, к которой машина подключена
политикой `cdgaxhyj77s3grhewcjf`.

### Что разложено на машине руками

cloud-init на принятой машине уже отработал (`status: done`) — до того, как
Terraform положил `user-data` в метаданные, — и второй раз не запускается.
Поэтому платформенная часть разложена по шагам шаблона вручную: часовой пояс,
пакеты (`docker.io` 29.1.3, `docker-compose-v2` 2.40.3, `jq`,
`unattended-upgrades`, `chrony`), все восемь файлов из `write_files` с их
правами, группа `docker` пользователю, службы и агент мониторинга. Метрики
`sys.*` с хоста `crm-uchetkin-prod` доходят до Cloud Monitoring.

Полное обновление пакетов (`package_upgrade: true`) на живой машине не
выполнялось — этим занимается `unattended-upgrades`.

Приложение выложено до появления CI/CD: образы собраны на самой машине из
`/opt/uchetkin/src` и помечены тегом `manual`, потому что в Container Registry
их ещё никто не публиковал. Остальное — как в `deploy/deploy.sh`: пароль базы
из Lockbox, миграции отдельным шагом, затем запуск. Снаружи `/health` отвечает
`200` и телом `{"status":"ok","db":"ok","version":"1.0.0"}`.

### Две ошибки, найденные на живой машине

Обе были в `cloud-init.yaml.tftpl` и обе исправлены:

1. **Агент мониторинга пропадал при каждой выкладке.** У
   `compose.platform.yml` не было своего имени проекта, Compose брал его из
   имени каталога — `uchetkin`, то же, что в `deploy/compose.yml`. Для выкладки
   агент оказывался чужим контейнером её же проекта, и
   `docker compose up -d --remove-orphans` из `deploy.sh` его сносил. Добавлено
   `name: uchetkin-platform`.
2. **Агент не поднимался вовсе.** Его конфигурация монтировалась на
   `/etc/yandex/unified_agent/config.yml`, а точка входа образа сама пишет этот
   файл из `config.tmpl.yml`. Под `:ro` она падала с «Read-only file system», и
   контейнер уходил в вечный перезапуск. Конфигурация теперь монтируется как
   `config.tmpl.yml`.

## Эксплуатация: мониторинг, логи, копии, сторож

Пункт плана `cloud-ops`. Что значит каждое оповещение, что делать и как
восстанавливать базу — [`docs/ops.md`](../docs/ops.md). Здесь — только как это
описано кодом и как применяется.

| Что | Где | Применено в dev |
| --- | --- | --- |
| Журналы контейнеров → Cloud Logging, 30 дней | `logging.tf`, маршрут `docker_logs` агента в `cloud-init.yaml.tftpl` | да, группа `uchetkin-dev-app` |
| Метрики Caddy (RPS, коды, время ответа) | `deploy/Caddyfile` (`metrics`, сайт `:2020`), `deploy/compose.yml` (порт на 127.0.0.1), маршрут `metrics_pull` агента | да |
| Служебные метрики машины (`uchetkin.*`) | `uchetkin-status` + таймер, `cloud-init.yaml.tftpl` | да, каждые 5 минут |
| Ежедневный и еженедельный `pg_dump` → бакет `ops` | `backup.tf`, `uchetkin-backup` + таймер | да, 02:30 по Екатеринбургу |
| Дашборды: машина, HTTP, база, балансировщик | `dashboards/` | да: `uchetkin-dev-vm`, `uchetkin-dev-http` (базы и балансировщика в dev нет) |
| Сторож: `/health`, диск, копии, 5xx, сертификат → Telegram и почта | `watchdog.tf`, `watchdog/index.js` | да, раз в минуту; Telegram и почта отложены по решению владельца 18.09.2026 — пока оповещения пишутся в Cloud Logging и в `watchdog/alerts.json` бакета `ops` |

**Дашборды — отдельный корневой модуль** `dashboards/` с провайдером,
прибитым к `0.222.0`. Провайдер с `0.223.0` по `0.228.0` (текущий) падает на
любом дашборде — «expected operation metadata to be CreateDashboardMetadata,
but got ''», — хотя API создаёт и обновляет доску успешно; проверено
18.09.2026 перебором версий на минимальной доске из одного текстового
виджета. Всё, что модулю нужно знать о контуре, он читает из выходов основного
состояния (`terraform_remote_state`). Применяется после основного модуля:

```bash
terraform -chdir=dashboards init -backend-config=backend-dev.hcl
terraform -chdir=dashboards plan -var-file=dev.tfvars -out=dev.tfplan
terraform -chdir=dashboards apply dev.tfplan
```

Когда провайдер починят — снять пин в `dashboards/versions.tf` и при желании
перенести файл обратно в корень.

**Алертов Monitoring в коде нет намеренно.** Ни Terraform-провайдер, ни
публичный API алертов и каналов оповещений не имеют — только консоль; почтовый
канал там принимает лишь учётные записи облака, Telegram требует привязки
аккаунта пользователя в консоли. Заказчику без администратора нужно
оповещение обычным языком в обычный Telegram и на обычную почту, поэтому
проверки и доставку делает сторож — Cloud Function по таймеру (`watchdog.tf`).
Каналы доставки — секреты Lockbox `<контур>-alerts` (`telegram_bot_token`,
`telegram_chat_id`) и `<контур>-smtp` плюс переменная `alert_email`; пока они
пусты, сторож пишет текст оповещения в Cloud Logging и помечает, что канал не
настроен. Проверка доставки без аварии:

```bash
yc serverless function invoke <контур>-watchdog -d '{"test": true}'
```

**Что применено руками на принятой машине.** cloud-init на ней второй раз не
запускается (см. «Что разложено на машине руками»), поэтому новые файлы
шаблона — конфигурация агента, `uchetkin-backup`, `uchetkin-status`, четыре
юнита systemd, дополненный `app.env` — разложены скриптом, который берёт
отрисованный `user-data` из метаданных ВМ и пишет `write_files` как есть;
контрольные суммы файлов на машине совпадают с шаблоном. `Caddyfile` и
`compose.yml` положены вручную теми же файлами, что в `deploy/` — следующая
выкладка привезёт их же.

**Найдено по ходу и исправлено:**

- класса хоста `b3-c1-m4` из `arch` в Managed PostgreSQL не существует
  (`resource preset … not available`); в `variables.tf` и `prod.tfvars` — `b2.medium`;
- Managed PostgreSQL снаружи слушает только 6432 (пул соединений), прямой 5432
  закрыт — `pg_dump`, `pg_restore` и приложение ходят через 6432;
- приложению к Managed PostgreSQL нужен `sslmode=no-verify` (или корневой
  сертификат облака) в строке подключения — с голым `sslmode=require` контейнер
  API до базы не достучался, это пункт `cloud-prod`;
- два авторитетных `yandex_kms_symmetric_key_iam_binding` на одну роль ключа
  перетирали друг друга; заменены на `_iam_member` по одному на держателя.

## Где живёт доменное имя

В коде его нет. Имя задаётся переменной `app_domain` в файле переменных контура,
и из него собирается всё остальное — адрес веб-приложения, адрес API, основа
адресов вебхуков, домен cookie. На ВМ это уезжает файлом `/etc/uchetkin/app.env`,
фронт получает свой адрес API из `/opt/uchetkin/config/frontend.json`. Ни сборка
фронта, ни код сервера домен не знают.

Проверить это можно так — вывод должен быть пустым:

```bash
grep -rn "sslip.io\|uchetkin.ru" --include="*.tf" --include="*.tftpl" --include="*.html" .
```

До боевого домена контуры живут на временных именах вида
`<статический адрес через дефисы>.sslip.io`: публичный сервис sslip.io
разрешает такое имя в сам адрес, ничьих DNS-записей для этого не нужно, и
Let's Encrypt выпускает на него настоящий сертификат — без него не работают ни
вебхуки Новофона, ни камера в браузере у поверителя. Проект независим от других
продуктов подрядчика (решение владельца 18.09.2026): чужих доменов, в том числе
поддоменов подрядчика, в контурах нет.

| Контур | Имя | Состояние |
| --- | --- | --- |
| dev (он же рабочий с 18.09.2026) | `84-201-139-101.sslip.io` | HTTPS включён 18.09.2026 (пункт `live-tls`), сертификат Let's Encrypt у Caddy; со старого `http://84.201.139.101` — редирект (`legacy_redirect_from`) |
| prod | `<адрес>.sslip.io`, адрес появляется при apply | не применялся; порядок в два шага — «Порядок применения», шаг 4 |
| боевой домен | `uchetkin.ru` | куплен 20.09.2026 (Reg.ru), зона и записи заведены в Cloud DNS этим описанием (`manage_dns_zone = true`); NS у регистратора ещё не переключены, система на домен не переведена — пункт `cloud-domain`, `docs/ops.md` |

Боевой домен подключается отдельным пунктом `cloud-domain`: меняется значение
одной переменной, всё остальное описание не трогается. Имя боевого домена
встречается в файле переменных контура (`dev.tfvars`) — в описании ресурсов его
по-прежнему нет, поэтому поиск выше остаётся пустым.

## Отличия от постановки

**Балансировщика в работе нет, и это решение `arch`, раздел 3.** Application Load
Balancer тарифицируется ресурсными единицами, минимум две в зоне — около 3 977 ₽
в месяц, больше, чем стоит кластер базы, и почти столько же, сколько сама ВМ. При
одной ВМ он не даёт ничего из того, ради чего его ставят: распределять нагрузку
не между кем, отказоустойчивости за ним нет. Терминацию TLS, сертификат Let's
Encrypt, проверки доступности и HTTP/3 делает Caddy на самой машине.

Описание балансировщика при этом написано целиком и лежит в `alb.tf` вместе с
сертификатом из Certificate Manager и проверкой здоровья `/health`. Включается
одной переменной:

```bash
terraform plan -var-file=prod.tfvars -var ingress_mode=alb
```

В режиме `alb` меняется и периметр: 443 снаружи открыт балансировщику, а ВМ
принимает только его трафик. Возвращаться к нему стоит, когда появится вторая
ВМ, понадобится Smart Web Security или выкладка без простоя. Пока нет ни одного
из трёх условий — это 47 700 ₽ в год за ничего.

**Сроки перехода в холодное хранение взяты из `arch`, раздел 7, а не «через год»:**
фото актов — 90 дней, записи разговоров — 30 дней в стандартном хранилище и год
до ледяного. Это переменные `acts_cold_after_days`, `calls_cold_after_days`,
`calls_ice_after_days`; если нужен ровно год для обоих бакетов — меняются числа
в файлах контуров.

**В dev нет Managed PostgreSQL** (`managed_postgres = false`): база поднимается
контейнером на той же ВМ. Так решено в `arch` — экономия около 2 600 ₽ в месяц.
Кластер, группа безопасности базы и пользователь в этом контуре не создаются,
а в `/etc/uchetkin/app.env` уезжает `PGHOST=postgres`.

## Что сделано для безопасности

- Снаружи открыты 443/tcp, 443/udp (HTTP/3) и 80/tcp. Восьмидесятый нужен для
  редиректа с `http://` и как резервный способ подтверждения домена; закрывается
  переменной `open_http_port` — Caddy тогда подтверждает домен через TLS-ALPN-01
  на 443.
- SSH — только по ключу и только с адресов из `ssh_allowed_cidrs`; `0.0.0.0/0`
  в этом списке запрещён проверкой переменной. Список пуст — правила 22/tcp нет
  вовсе. Пароли на машине выключены совсем (`sshd_config.d/10-uchetkin.conf`
  из cloud-init: `PasswordAuthentication no`, `PermitRootLogin no`,
  `AuthenticationMethods publickey`), вход root закрыт, сессия без активности
  рвётся через десять минут. Переменная `enable_oslogin` переводит вход на
  учётные записи облака — тогда к машине применяется и двухфакторная
  аутентификация организации.
- База наружу не смотрит: к ней ходит только ВМ приложения, правило привязано к
  группе безопасности, а не к диапазону адресов.
- Бакеты приватные: ни чтения, ни списка для анонимов. Приложению выданы роли
  `storage.viewer` и `storage.uploader` **на конкретный бакет** — это чтение и
  запись без удаления: объект, попавший в акт, приложение стереть не может даже
  при ошибке в коде. Версионирование включено, автоудаления нет.
- Сервисный аккаунт приложения не имеет ролей на каталог целиком, кроме записи
  метрик и логов и чтения образов из реестра: у этих трёх ролей уровня
  «только свой ресурс» в облаке просто нет.
- Пароль базы и ключи подписи токенов генерирует Terraform и кладёт в Lockbox.
  Статический ключ для подписанных ссылок пишется сразу в Lockbox
  (`output_to_lockbox`) и в состоянии Terraform не появляется.
- Состояние Terraform лежит в бакете с версионированием, а не на чьём-то ноутбуке.
  В нём есть пароль базы — доступ к бакету состояния приравнивается к доступу к базе.
- У бакетов стоит `prevent_destroy`, и у боевого кластера базы —
  `deletion_protection`. `terraform destroy` на них спотыкается намеренно, в том
  числе в dev: чтобы снести контур, защиту нужно снять руками и осознанно.
- Бакеты шифруются своим ключом из KMS (`kms.tf`), а не общим ключом облака:
  право расшифровки выдано ролью `kms.keys.encrypterDecrypter` на сам ключ,
  обращения к ключу видны в аудите, ключ можно отозвать, не трогая бакеты.
  Версия ключа меняется раз в год сама (`kms_rotation_period`).
- Audit Trails (`audit.tf`) пишет в отдельный бакет два журнала: действия в
  каталоге и обращения к объектам хранилища — то есть к фотографиям актов и
  записям разговоров. У приложения прав на этот бакет нет, у аккаунта аудита —
  только `storage.uploader`: дописать можно, стереть нельзя.
- Перед балансировщиком — профиль Smart Web Security (`sws.tf`): базовый набор
  правил OWASP и защита от ботов, вебхуки внешних систем пропускаются мимо
  браузерной проверки. Профиль создаётся только при `ingress_mode = "alb"`:
  привязка у Smart Web Security одна — виртуальный хост ALB.
- Правила входа в само приложение (длина пароля, блокировка после пяти неудачных
  попыток, срок жизни сессии, срок хранения журнала действий) заданы переменной
  `app_auth_policy` и уезжают на ВМ в `/etc/uchetkin/app.env`. Сервер их пока
  не читает — его ещё нет, это пункты `be-api` и `be-audit`.

Сводная таблица «мера — где настроена — статус», включая то, что делается руками
в консоли облака и что ещё не сделано, — в [`docs/security.md`](../docs/security.md).

тратится вовсе. Сверить и добавить в таблицу — при первом включении `alb`.

## Что меняется при переезде на боевой домен

Пункт плана `cloud-domain`, выполняется после запуска. Адрес системы живёт ровно
в одной переменной, поэтому переезд — это правка файла переменных контура и
перевыпуск сертификата, а не переписывание кода. Пошаговый порядок дня переезда
с проверками — `docs/ops.md`, «Переезд на боевой домен»; здесь — что для него
описано в Terraform и что из этого за какой переменной.

| Что | Переменная | Ресурс |
| --- | --- | --- |
| Имя системы | `app_domain` | всё, что считается в `locals.tf`: адреса в `app.env`, `frontend.json`, CORS бакета снимков, `APP_URL` сторожа |
| Зона в Cloud DNS и A-записи | `manage_dns_zone = true`, `dns_zone_domain`, `dns_ttl` | `dns.tf`: `yandex_dns_zone.main`, `yandex_dns_recordset.app` и `…www`; NS у регистратора — `ns1.yandexcloud.net`, `ns2.yandexcloud.net` (выход `dns_zone`). Пока `app_domain` ещё временный, A-запись домена стоит на вершине зоны (`locals.tf`, `app_in_zone`) |
| Сертификат | `tls_enabled = true` | Caddy на ВМ (`ingress_mode = vm`): получает и продлевает сам, ALB и Certificate Manager в работе нет (`alb.tf`, «Отличия от постановки») |
| Почтовый домен для Яндекс 360 | `mail_records_enabled`, `mail_verification_txt`, `mail_dkim_public_key`, `dmarc_policy`, `dmarc_rua` | `dns.tf`: MX `mx.yandex.net`, TXT SPF `v=spf1 redirect=_spf.yandex.net` и подтверждение на вершине зоны, `mail._domainkey` (DKIM), `_dmarc` |
| Редирект со старых адресов | `legacy_redirect_from` | cloud-init пишет `/etc/uchetkin/caddy.d/legacy.caddy`, `deploy/Caddyfile` подключает каталог, `deploy/compose.yml` монтирует его; действует только при `tls_enabled = true` |

Что при этом **не** в Terraform и делается руками в кабинетах: регистрация
домена на ИП у регистратора и делегирование NS; добавление домена в Яндекс 360
(оттуда берутся строки подтверждения и DKIM); адрес приёмника вебхуков в кабинете
Новофона; ограничение ключа JS API Яндекс Карт по домену; пароль нового ящика
в Lockbox `smtp` и `NOTIFY_FROM` в `app.env`.

Проверка шаблона (файл редиректа собирается из списка, блок с `redir … permanent`
на месте) входит в `check_cloud_init.py`; сама конфигурация Caddy с каталогом
`caddy.d` проверена `caddy validate` 18.09.2026 во всех четырёх состояниях —
каталога нет, пустой, файл из одного комментария, файл с блоком.

## Что не проверено и почему

Контур dev применён против живого облака 18.09.2026, поэтому список короткий.

Проверено на деле: `init` с бэкендом в Object Storage, `import` ВМ, сети и
подсети, `apply` с кодом 0 и повторный `plan` — «No changes»; имена ролей на
бакетах (`storage.viewer`, `storage.uploader`) и на ключе KMS; образ
`ubuntu-2404-lts-oslogin`; квоты каталога хватило на всё описанное без правок;
установка `docker.io` и `docker-compose-v2` из репозиториев Ubuntu 24.04;
конфигурация агента мониторинга и доставка метрик `sys.*` в Cloud Monitoring;
чтение секретов из Lockbox сервисным аккаунтом самой машины; вход в Container
Registry по её же аккаунту; миграции и ответ `/health` снаружи кодом 200.

Осталось непроверенным:

- **Managed PostgreSQL**: класс хоста `b3-c1-m4`, версия 16, окно резервного
  копирования. В dev базы как сервиса нет, а prod не применялся.
- **Всё, что включается вместе с `ingress_mode = "alb"`**: балансировщик,
  Certificate Manager, Smart Web Security, служебные диапазоны проверок
  здоровья. Режим выключен в обоих контурах.
- **Контур prod целиком** — не применялся. Свободность имён
  `uchetkin-prod-acts` и `uchetkin-prod-calls` не проверялась.
- **Снимки загрузочного диска** — в dev выключены (`vm_snapshot_schedule =
  false`). Учения по восстановлению базы проведены 18.09.2026 на временном
  кластере Managed PostgreSQL — `docs/ops.md`, «Протокол учений»; там же
  замеры. Восстановление самой машины из снимка не проверялось.
- **Каналы оповещений сторожа** — секреты `alerts` и `smtp` пусты, `alert_email`
  не задан: оповещения доходят до Cloud Logging, но не до людей. Проверка
  доставки — `yc serverless function invoke … -d '{"test": true}'` после
  заполнения (`docs/ops.md`, «Как включить каналы»).
- **Выкладка через GitHub Actions** (пункт `cloud-cicd`). Сейчас на машине
  образы, собранные на ней же с тегом `manual`; путь «сборка в Actions → push в
  Container Registry → `docker compose pull` на ВМ» не прогонялся.
- **Стоимость** — расчёт по прайс-листу, а не счёт. Ни одного закрытого
  расчётного периода ещё не прошло.
